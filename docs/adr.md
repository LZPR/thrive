# ADR · Thrive 学习模式

只记录「如果不写下来，下次一定会再踩一遍」的决策。凡是读一遍代码就能想明白的，不记。

状态标记：`已定` / `待验证`

---

## ADR-001 · 用工具注册门控实现模式开关，而不是在生成流程里分支

**背景**：需要一个"开启/关闭学习模式"的开关，且关闭时必须让模型完全察觉不到插件的存在。

**决策**：始终调用 `registerFunctionTool` 注册全部工具，用 `shouldRegister: () => isEnabled()` 做每请求判断。

**理由**：
- ST 的 `ToolManager.registerFunctionToolsOpenAI` 只在 `tools.length > 0` 时写入 `data.tools`（`public/scripts/tool-calling.js:412`）。所有工具的 `shouldRegister` 返回 false 时，请求体与原生完全一致。
- 反向做法（开关时 register/unregister）会改变 `tools` 数组的顺序与内容，而 `tools` 位于请求头部，任何顺序变化都会让整条前缀缓存失效。

**后果**：工具在应用启动时就固定注册，用户在设置里切换模块不需要重载；`shouldRegister` 必须是同步廉价判断。

## ADR-002 · 学习块注入在对话尾部，位置可配但默认尾部

**背景**：注入一段系统提示词让模型进入学习状态，同时不希望破坏缓存。

**决策**：默认 `setExtensionPrompt(key, text, IN_CHAT, 0, false, SYSTEM)`，即插在消息数组最末尾。设置项允许改为头部（`IN_PROMPT`）或完全不注入。

**理由**：
- `populationInjectionPrompts` 对消息数组先 `reverse()` 再按 depth 插入，最后再 `reverse()` 回来（`public/scripts/openai.js:810-875`）。depth 0 落在最后一位。
- 尾部注入不改变前缀，开关模式只是一次"末尾增减"；头部注入会让整段 system 前缀失效，开关一次就要全量重新 prefill。

**权衡**：尾部块每轮都要重新计费（约 680 字，折合约 500 token），头部块可被缓存但开关代价高。本插件开关频繁，选尾部。长会话、极少开关的用户可自行改头部。

## ADR-003 · 学习块里的 `{{char}}` / `{{user}}` 必须由插件替换

**背景**：提示词里不能用"你/我"指代，否则角色扮演场景下有歧义。

**决策**：注入前先调 `context.substituteParams(text)`。

**理由**：ST 组装 systemPrompts 时直接取 `prompt.value`（`openai.js:1463`），扩展提示词原样进入，不走替换。1.19 虽然给 PromptManager 加了 `preparePrompt() → substituteParams`，但那条路只覆盖头部提示词集合；默认的尾部注入（`IN_CHAT`）走 `getExtensionPrompt()`，确定不经过它。两条路径行为不一致，统一由插件替换才能保证两种位置表现相同。

## ADR-004 · 知识只落原生通道，插件不持有"学到了什么"

**背景**：需要在关闭模式后仍然不失忆，同时希望模式与原版对话解耦。

**决策**：学习成果 100% 写入世界书与角色卡字段。插件不维护索引、摘要、向量或任何"知识状态"。唯一的插件侧状态是操作性的（本轮读了什么、有没有一个待确认的补丁、上一版备份）。

**理由**：模式切换时不需要同步任何东西——知识由 ST 自己的世界书扫描与角色卡装配带进上下文，与插件开关无关。

**后果**：
- 关闭模式 = 不注入、不注册工具，其余一切照旧。
- 卸载插件后，学到的内容依然生效。这是特性，不是残留。

## ADR-005 · 世界书即时写、不做 patch；patch 只用于角色描述

**背景**：曾考虑所有写入都先暂存成补丁，确认后统一应用，以换取撤销与批量降缓存失效。

**决策**：世界书写入立即落盘。只有角色描述的修改走 patch。

**理由**：
- 世界书是动态的：条目是否进入 prompt 取决于关键词命中，改动常常根本不改变前缀，暂存带来的缓存收益接近零。
- 世界书条目的"读—改—写"跨插件和 ST 编辑器两侧，维护一份暂存视图与真实文件的同步成本高于收益。
- 角色描述相反：它每次都在 system 前缀里，改一次必然让缓存失效，批量合并的收益最大。

**后果**：世界书没有撤销栈之外的保护；误写要靠撤销槽位或手动编辑。

## ADR-006 · patch 表达的是"磁盘 vs 暂存"的单一 diff，不是操作流水

**背景**：早期设计是"每次写入生成一条补丁，排队应用"。

**决策**：同一目标永远只有一个 patch 对象，字段只有 `before`（磁盘文本）、`after`（暂存文本）、状态与时间。

**理由**：
- 多条补丁会产生链式依赖：第 1 条被丢弃，第 2 条基于第 1 条的基准就失效，只能连锁标记冲突。
- 用户想看的是"现在会变成什么样"，不是"模型按了哪几下"。
- 单 diff 让"模拟叠加"变成一次文本替换，读取时不需要重放操作序列。

**后果**：用户在面板里只能接受或拒绝整份改动，不能逐条挑选。这是有意的——patch 是只读的。

## ADR-007 · 先读后写 + 内容哈希；自己写入产生的新版本视为已读

**背景**：需要防止模型基于陈旧认知覆盖内容。

**决策**：两重校验。
1. **轮次登记**：用户每发一条消息清空读取表；写入时该目标本轮没读过 → `READ_REQUIRED`。
2. **版本校验**：读取时记录内容哈希；写入时若当前哈希与记录不符（无论谁改的）→ `STALE_READ`。
3. **例外**：插件自己写入成功后立即登记新哈希，视为已读。

**理由**：没有第 3 条，模型在同一轮里 `read → write A → write B`（同一目标）会卡在第二步——因为"条目已变化"永远为真。这条不是放宽限制，是消除死锁。

## ADR-008 · `constant` 锁死为 false

**背景**：曾打算让模型自行决定条目是否常驻（constant），以便"全局设定"总能出现在上下文里。

**决策**：不支持。新建与改写一律 `constant: false`，模型无权设置。

**理由**：关键词可自由多写 + 常驻可自由开启 = 上下文预算失控。模型完全有能力把所有条目设为常驻，而每条常驻都会永久占用上下文并让每次改动都破坏缓存。

**后果**：全局设定只能靠关键词触发。写入时必须至少给 1 个关键词，否则是永不触发的死条目（见 ADR-009）。

## ADR-009 · 新建条目必须至少 1 个关键词，且拒绝空内容

**背景**：`constant` 关闭后，没有关键词的条目永远不会进入上下文。

**决策**：`lore_write` 新建条目时 `keys` 为空 → 拒绝（`NO_KEYS`）；`content` 为空白 → 拒绝（`EMPTY_CONTENT`）。

**理由**：
- 无关键词 = 写进黑洞，用户以为记住了其实没有。
- 允许空内容等于给了一个事实上的删除工具，而本插件明确不提供删除（见 ADR-011）。

这两条不是玩法限制，是正确性要求。

## ADR-010 · 角色描述不加区域标记，允许自由改写

**背景**：最初设计是在描述里追加 `【Thrive · 学习笔记】` 段落作为写入区，读只读该段、只追加。

**决策**：取消标记。模型可以增删改描述里的任意内容，写出来的文字必须像原有人设一样自然（不用列表、不加小标题）。

**理由**：本插件的使用场景是"从零开始养一个角色"，不是改造成熟卡。区域标记会让文本看起来像机器贴上去的，破坏角色质感。取消标记后 `desc_read` 必须返回整段描述，成本更高，但换来文本自然。

**代价**：
- 读取成本从几百字涨到一两千字。
- 不再有"一键删掉学到的内容"，只能靠 patch 的 diff 或手动编辑。
- 直写模式下一次 rewrite 可以覆盖用户原文 —— 由 ADR-016 的快照兜底。

## ADR-011 · 不提供删除工具；`disable` 也不给

**背景**：世界书条目会写错、会重复。

**决策**：工具面没有删除、没有停用。模型唯一的"更正"手段是改写该条目的内容。

**理由**：删除是最容易被 prompt injection 利用的能力，收益却很低——用户自己能在世界书编辑器里删。

**后果**：模型写重复条目后无法自行清理，只能请用户处理。这是有意的权限收缩。

---

## ADR-012 · 世界书与角色描述拆成两个独立开关，且不降级

**决策**：两个模块可分别开关；关闭时对应工具不注册（模型看不见）。目标类型与可用模块不符时**直接拒绝**，绝不自动改道到另一个模块。

**理由**：如果"世界书已关闭"时插件偷偷把内容写进角色描述，模块开关就形同虚设，用户也无法预期内容去了哪。

**配套**：两个模块都关时禁止启用学习模式（否则是空转，用户以为在学习）。

## ADR-013 · 工具调用日志：当轮保留，下一轮移出上下文

**背景**：ST 会把工具调用渲染成一条 `is_system` 消息塞进 chat，内容是一段带 JSON 的 `<details>` HTML。只要全局开着 function calling，这条消息就会被计入上下文（`public/script.js:4496` 的 `coreChat` 过滤条件）。

**决策**：当轮保留（模型要靠它写回复）；用户发出下一条消息时，删除这些消息的 `extra.tool_invocations`，使其被 ST 的过滤条件排除，但保留 `mes` 继续显示。

**理由**：HTML + JSON 极度费 token，且会随对话线性增长；删除 `tool_invocations` 是最小侵入的做法——不需要改写 prompt，不需要拦截事件，直接复用 ST 自己的过滤逻辑。

**代价**：每次清理会在历史中间段产生一次缓存断点。一次性，之后稳定。

## ADR-014 · 不使用 stealth 工具

**背景**：ST 支持 `stealth: true`，工具调用不显示、也不触发后续生成。

**决策**：不用。

**理由**：`script.js` 在 `invocationResult.stealthCalls.length` 时直接 `return`，不进入递归生成（`public/script.js:5421`、`5546`）。也就是说 stealth 工具调用会**吞掉这一轮的正文回复**。本插件需要在写完记忆后继续说话，stealth 与需求冲突。

---

## ADR-015 · 工具只暴露允许修改的字段，读也不返回其它字段

**决策**：角色侧只读写 `description`。`personality`、`scenario`、`first_mes`、`mes_example` 既不写、也不读。

**理由**：不返回就不可能被改写。相比"在提示词里禁止修改"，减少可读字段是结构性防御——模型连内容都看不到，就不会产生"顺手调整性格"的念头。

---

## ADR-016 · 直写前保留快照，与 patch 开关解耦

**背景**：patch 是可选功能。关闭后，一次 rewrite 就能覆盖角色描述且不可逆。

**决策**：直写前把当前值存入内存槽位；世界书按条目保留最近一次前值（最多 10 条），描述保留最近 1 版。面板提供"恢复上一版"。

**理由**：这是"手滑保险"，不是版本控制系统。它不改变写入语义、不阻止任何操作，成本只有一个槽位。

---

## ADR-017 · 换书时提醒模型，而不是阻止

**背景**：可写世界书允许中途切换，切换后旧条目不在新书里。

**决策**：`lore_read` 发现当前书与上次不同时，返回 `switched: true` 与一句说明（不要重复记录）。

**理由**：模型会以为自己"忘光了"，从而把旧内容原样重写一遍。提醒比拦截便宜，也不会挡住正常使用。

---

## ADR-018 · 读范围与写范围分离，且可配置

**决策**：写永远只作用于用户指定的那一本；读可以是"只看可写书"或"可读所有绑定到当前角色的书"，由设置决定。

**理由**：两种用户都存在——只关心自己那本的，和需要参照既有世界设定的。读范围放宽不增加写入面，风险可控；但读取返回必须带 `source_book`，否则模型不知道条目来自哪本，改写时容易写错书。

---

## ADR-019 · 不做每轮写入配额

**决策**：不限制"每轮最多写几条"。

**理由**：ST 自身对工具调用递归有 `RECURSE_LIMIT = 5` 的硬上限（`tool-calling.js:255`），已经提供了天然约束。额外配额属于"非必要硬限制"，与"靠提醒而非强制"的设计原则冲突。真正的护栏放在 append 的长度上限上——那一条是为了防止条目无限膨胀，不是为了防止频繁写入。

---

## ADR-020 · 工具是否可用一律问 ST，不自己推断

**背景**：1.13 时代判定简单——后端是 chat completion 且 `function_calling` 打开即可。1.19 起增加了模型级检查，还改了后处理的判定方式。

**决策**：可用性判断只调 `ctx.isToolCallingSupported()`，不复制 ST 的判断逻辑。

**理由**：
- 1.19 的 `isToolCallingSupported(settings, model)` 会按来源分别检查模型能力：OpenRouter 看 `supported_parameters` 是否含 `tools`、Mistral 看 `capabilities.function_calling`、Fireworks 看 `supports_tools`、Workers AI 看 `properties` 等。
- 后处理从"开了就禁用"变成白名单 `[NONE, MERGE_TOOLS, SEMI_TOOLS, STRICT_TOOLS]`。选 `merge` / `semi` / `strict`（不带 `_tools`）仍然禁用工具，但选 `merge_tools` 等就能用。
- 还有特例：`gpt-6-astra` 走 Responses API，即便设置全对也判否。

**后果**：诊断页只能给"为什么不行 + 去哪改"，无法穷举所有组合；这是有意的——插件不该成为 ST 能力判定的第二份实现，一旦 ST 加新来源就会失真。

## ADR-021 · 不自动激活可写书，只把"写了会不会生效"说清楚

**背景**：真实模型端到端测试暴露一件事——条目写进了文件，但 `getWorldInfoPrompt` 返回长度是 0。原因不在写入，而在 ST 只扫描**已激活**的书。用户不手动勾选，插件记得再准也永远想不起来，而工具返回还写着"最迟下一轮生效"。

**决策**：插件不碰激活列表。改为三处如实说明：`lore_read` 总览的 `note`、`lore_write` 的 `note`、设置面板的可写书提示（`§11.4`）。

**理由**：
- `selected_world_info` 没有公开 API。能做的只有改 `#world_info` 的 `value` 再 `trigger('change')`，这会连带 `saveSettingsDebounced()` 与 `WORLDINFO_SETTINGS_UPDATED` 事件——等于替用户做了一次他不知情的设置变更，且依赖 DOM 结构，ST 改版就碎。
- 激活哪几本书是**用户的世界观边界**：多激活一本，就可能让别的角色带上不该有的设定。
- 反过来，不激活却又写进去，等于给了一个"看起来成功、实际无效"的工具——这比拒绝更糟。所以"说清楚"是必须的，不是可选的。

**代价**：
- 用户第一次用必须自己去勾一次书。面板警告只在他打开扩展设置时可见。
- 模型被要求"提醒用户勾选"，会多出半句台词。接受。

**判定方式**：读 `#world_info` 的 `selectedOptions`（角色/聊天绑定的书直接算已扫描，不需要激活）。三态返回，读不到面板时判 `null` 并按"已激活"处理——宁可漏报，不可误报"你没激活"。

## ADR-022 · 快照兼作写入记录，一条数据两用

**背景**：面板要显示"已写入"列表（时间、标题、动作、字数），每条还要能"恢复写入前"。按字面理解这是两件事：一份展示用的流水 + 一份恢复用的快照。

**决策**：合成一条 `backups.lore` 记录：`{ id, book, title, action, before, beforeKeys, chars, at }`。10 条上限同时是"能退几步"和"面板显示几行"。

**理由**：
- 两份数据必然不同步。流水比快照长（面板说 20 条，实际只能恢复 10 条）就要在 UI 里解释"这条不能恢复"，而用户看不到差别；流水更短又浪费槽位。
- `id` 让恢复不依赖下标：新写入会整体前移，按 index 定位会在一次写入后指错条目。
- `action` 决定恢复语义：`rewritten` 写回内容；`created` 写入前不存在，恢复 = 删除。这两件事不能共用一个"写回旧正文"的动作。

**代价**：
- 老对话里的快照只有 `{ book, title, before, at }`，`action` 靠 `before` 是否为空推断，`id` 由 `at + index` 补齐。补出来的 id 必须可重复计算，否则"点了恢复"和"重绘后拿到的 id"对不上。
- 删除条目发生在用户点「撤销新建」时。ADR-011 说的是不提供删除**工具**（模型不能删），不是用户不能撤销自己刚看到的一次写入。

## ADR-023 · 日志处理只作用于"纯 Thrive"的消息

**背景**：`TOOL_CALLS_PERFORMED` / `MESSAGE_SENT` 拿到的是一批调用，但 ST 把**同一轮所有工具**的调用合并成一条 `is_system` 消息。如果用户同时装了别的工具型扩展，这条消息里会混着别人的调用。

**决策**：只有当一条消息里的调用**全部**是 Thrive 工具时才处理（压缩 `mes` 或删除 `extra.tool_invocations`）。混合消息原样留给 ST。

**理由**：
- 改写 `mes` 是替别人决定日志长什么样：别的扩展可能特意渲染了可展开的参数、图片或链接。
- 删除 `tool_invocations` 更严重——那条消息会整条被排除出上下文，别人的调用记录跟着一起消失，而且没有任何提示。
- 反过来，为了"只摘掉自己那部分"去改写混合消息，需要重排整个 `<details>` 块或删数组元素，两种做法都在猜别人的数据结构。

**代价**：装了其他工具扩展时，那些轮次的日志不会变短。这个代价可以接受：默认安装下不会有混合消息，而混装工具扩展本来就是少数场景。

## ADR-024 · 工具不可用时禁止开启学习模式

**背景**：诊断已经能判断"环境不支持 tools"，但开关本身仍然可点。此时开启的结果是：徽章亮着"学习"、
注入照常发生，模型却收不到任何工具——和"两个模块都关着"是同一种假象。

**决策**：`isToolCallingSupported()` 为 false 时徽章置灰；点击只提示第一条未通过的原因与改法，
不改变 `enabled`。已开启的对话**不自动关闭**——环境可能只是临时换了个模型。

**理由**：
- 与 ADR-012 的"两个模块都关时禁止启用"同构：不允许出现"看起来在学、实际学不到"的状态。
- 与 Step 07 的双关兜底不同，这里不自动关闭：模块开关是用户的稳定配置，模型/后端是随时会变的环境，
  自动关掉会在用户切回可用模型时把状态也弄丢。
- 只报第一条原因而不是列全部：一次改一处，改完诊断会自己更新（监听相关控件的 change 事件）。

**代价**：用户想"先开着，等会儿换模型"时开不了，得先切模型。这个顺序反而更符合因果。

## ADR-025 · 被动学习只"借"一轮，而不是常开

**背景**：用户希望"不点开关也能学一点"，同时要求"已经开着主动时不要重复触发"、
"触发要有明显提示"。直接的做法是让判据把 `enabled` 置为 true，过一会儿再置回 false。

**决策**：新增一个与 `enabled` 并列的、只在这一轮有效的一次性记号（`pending`）。
`isLearningActive() = enabled || pending`，注入与 `shouldRegister` 都只认它。

**理由**：
- **不改用户的状态**。用 `enabled` 开开关就得自己负责关，中途报错、切对话、刷新页面都会留下
  "自己亮起来的学习模式"。记号是可丢的：读不到就是没有，不会污染徽章。
- **一个判据，两个出口**。注入和工具注册共用一个函数，避免出现"块进去了、工具没注册"的半开状态——
  这类不一致排查起来最费时间，而且模型只会表现为"不听话"。
- **结算点选在角色消息落盘**，不是 `GENERATION_ENDED`。后者在点停止时也会发，扣掉记号等于
  白白浪费一次学习；`MESSAGE_RECEIVED` 只在真的有角色消息入栈时才有。
- **同一轮不重复触发**：结算时记下这一轮用户消息的哈希。角色把关键词复述一遍（"我记住了"）
  不该再开一轮，否则用户配了"记住"就会连续两轮都在学。

**代价**：
- 记号是对话级状态，切到别的对话看不见它——这符合预期（学的是这场对话），但"我在 A 对话挂了一个"
  只能在 A 的徽章上看。
- 判据是全局设置，被动开关也是全局的。想给某个对话单独关掉，只能用主动开关覆盖（开着主动即不触发）。

## ADR-026 · 写完就刷新 ST 的编辑器，而不是等用户关面板

**背景**：两条写入路径都会撞上同一件事——ST 的编辑器里存着一份**快照**，不是磁盘的引用。

- 角色编辑面板：`saveCharacterDebounced` 提交的是 `#form_create` 的**整张表单**。
- 世界书编辑器：`worldInfoCache` 是 `StructuredCloneMap({ cloneOnGet: true })`，`loadWorldInfo`
  每次返回深拷贝；编辑器拿自己那份渲染，之后任何一次输入都用它 `saveWorldInfo(name, data)`。

两份快照的共同点：**只要用户在编辑器里动一下，旧内容就整块盖回去**。世界书那条更狠——它盖的是
整本书，不只是被写的那一条。

**决策**：写入成功后，如果对应的编辑器正开着目标（角色面板在编辑这个角色 / 世界书编辑器停在这本书），
就把编辑器刷到最新状态，不等用户关面板：

- 角色描述：只覆盖**内容没被用户改过**的文本框（判据是"框里的值等于写入前原文"，换行先归一化）。
  用户改过的框不硬盖，面板改显示"编辑框里还是别的文字"并给一个按钮（现名「填入编辑框」，
  见 ADR-036）。
- 世界书：调 `reloadWorldInfoEditor` 让编辑器重新 `loadWorldInfo` 一份新拷贝（闭包里那份拿不到，
  `updateEditor` 也是拿它重画，只能整块重绘），然后还原搜索词、页码、展开着的抽屉、滚动位置。

**理由**：
- 快照是**引用层面**的问题，没法靠"再写一次"解决：写多少次，编辑器手里那份还是旧的。
- 反过来"提醒用户关掉面板"是把问题推给人：他关面板之前随手动一下 Order 就已经毁了一次写入，
  而面板当时显示的是"已写入"，等发现时只能从聊天记录里的 `patch.after` 捞。
- 世界书只能整块重绘：`data` 是 `displayWorldEntries(name, data)` 的闭包变量，没有对外句柄。

**代价**：
- 世界书重绘会重排列表。搜索词/页码/抽屉/滚动都做了还原，但**输入焦点**回不去（用户正在改的那格
  需要重新点一下）。写入与用户按键撞在同一毫秒的窗口没有被消除。
- 角色描述那条留了一个"用户改过就不动"的例外：这种情况下磁盘是对的、框里是旧的，只能靠面板上的
  按钮或用户自己关面板，代码无法两全。

## ADR-027 · 数值上限集中定义，读时夹取而不是改写设置

**背景**：软阈值 / 硬上限 / 返回条数 / 快照槽位 / 日志长度原本是常量，散在 `targets.js`、
`tools.js`、`store.js`、`trace.js` 四处。开放成设置项最自然的写法是每个模块各写
`Number(settings.x) || 常量`——四处默认值、四套范围校验、四种脏数据处理。

**决策**：新增 `src/limits.js` 作为唯一定义处：

- `LIMIT_SPECS`：每个数字的默认值、可输入范围与步进。`DEFAULT_SETTINGS` 直接铺开它的默认值表。
- `readLimit` / `readLimits`：读取时夹取，0 / 空 / 非数字 / 超范围一律回落默认值；
  `readLimits` 额外把软提醒封顶到硬上限。
- 设置页的 `min` / `max` / `step` 由 `LIMIT_SPECS` 灌进 DOM，模板里不写第二份范围。

**理由**：

- 这些数字直接决定"这次写入是被拒还是通过"。`Number(x) || 常量` 对 0 是失效的（0 是 falsy，
  会被当成没填），对负数则会把 `> hardLimit` 变成永远成立，必须有一处统一处理。
- 软提醒与硬上限不是两个独立数字：软 > 硬意味着内容在被拒之前根本收不到提醒，这个组合没有意义。
  与其在设置页拦住用户（填完一个再回头改另一个，很难理解），不如在生效时按硬上限算，
  再把"当前生效"的实际值写出来。
- 设置页的范围若与夹取逻辑分开维护，迟早出现"输入框允许 5000、实际被夹到 2000"。

**代价**：

- 每次工具调用多一次 `readLimits`（十几个 clamp），可以忽略，但每个模块都得记着走它，
  不能再直接摸 `settings.hardLimitEntry`。
- 用户填的数字与实际生效值可能不同，只能靠「当前生效」那一行说明，输入框本身表达不了。
- 记录槽位调小时，`getState` 会立刻裁掉多余的历史记录（不可恢复）。选"立刻裁"而不是
  "下次写入才裁"，是为了让"面板显示几行"和"数组里有几条"永远一致，不出现两套行为。

## ADR-028 · 设置项按用途分组折叠，复用 ST 原生抽屉

**背景**：设置页从 4 个开关长到二十多项（Step 14 一次加了 12 个数字），整页展开要滚很久，
找一项得先扫一遍全部标题。

**决策**：把设置项按用途分成六组，每组是一个嵌套的 ST 原生 `.inline-drawer`：

| 组 | 内容 |
|---|---|
| 基本开关 | 当前对话状态、新对话默认开启、徽章 |
| 被动学习 | 自动学习开关、条数间隔、关键词、现在触发一次 |
| 写入目标 | 两个模块、可写书、读取范围、描述改动暂存 |
| 数值与上限 | 12 个数字 + 恢复默认 |
| 提示词 | 注入位置、通用 / 主动 / 被动三段学习块、压缩指令 |
| 日志与面板 | 旧日志清理、记录面板尺寸 / 透明度 |

默认全部收起，环境诊断固定在外层、不参与折叠。

**理由**：

- ST 的点击处理是 `$(document).on('click', '.inline-drawer-toggle')`，用
  `closest('.inline-drawer')` 找外壳、再用 `> .inline-drawer-header` / `> .inline-drawer-content`
  取自己那一份。也就是说**嵌套天然可用**，内层点开不会连带外层，多个组也能同时开着。
- 默认收起不需要自己写：ST 的 `.inline-drawer-content { display: none }` 就是初始状态，
  点击时 `slideToggle` 才把行内 display 打开。自己再维护一个 open/closed 状态只会和它打架。
- 不写自定义折叠逻辑，也就没有"动画结束时机""状态与 DOM 不同步"这类问题。
- 面板绑定全部按 id 取元素，移动 DOM 不影响任何已绑定的处理器（Step 15 只改了模板与样式）。

**代价**：

- 展开状态不持久化：刷新页面后回到全收起。"上次看到哪"要靠再点一次，但换来的是每次打开
  设置页都是同一份确定的初始状态。
- 折叠标题上的说明文字在窄屏会被省略号截断（`overflow: hidden`），只能作为提示，不能当完整说明。
- 依赖 ST 的抽屉实现：如果哪天 ST 把 `inline-drawer` 的类名或点击委托改掉，分组会全部展平。
  这属于"跟着平台走"的选择——自己写一套反而要跟着主题和移动端适配一起维护。

## ADR-029 · 徽章退成「面板开关」，模式切换搬进浮动面板

**背景**：徽章原本是「主动 ｜ 被动」两段的胶囊，直接挂在 `#leftSendForm` 里。三个问题叠在一起：

1. **占地方**：两段文字按钮横在输入框旁，本来就拥挤的一行被吃掉一截；
2. **不合群**：ST 那一排是固定尺寸（`--bottomFormBlockSize`）、无边框、默认 70% 透明的图标按钮，
   胶囊的尺寸随文案走，宽度、圆角、边框都不一样；
3. **会被拉伸**：`#leftSendForm` 是 `display: flex` 容器，胶囊用 `width/height: auto`，
   高度跟着容器走，看起来比旁边图标高一头。

**决策**：

- 徽章缩成**一个固定尺寸的图标**（宽高都取 `--bottomFormBlockSize`、`flex: 0 0 auto`），
  只做一件事——开 / 关浮动面板；`/thrive panel` 打开的是同一个面板。
- 「主动 / 被动」两个开关搬进面板的第一段（模式），每个开关配一句"它管什么"，
  另有「本次待学习」与不可用原因。
- 徽章不再画额外的点/圈，状态用**图标本身**表达：强调色 = 主动开着，
  Em 掺正文色 = 只有被动开着，待学时图标呼吸；待确认计数浮在右上角。
- 面板取消"只剩标题栏"的收起态：徽章已经承担了这个角色，面板要么整块打开，要么整块隐藏。

**理由**：

- 35px 的方块里塞两段文字（更别说状态点）怎么放都比旁边的图标更"外来"，越加越脏；
  真正需要看状态的时刻，用户已经在面板里了。
- 开关从徽章搬到面板后第一次有了写说明的地方：主动是对话级、被动是全局且只借一轮——
  这两句话以前只能塞进 `title`，得悬停才知道。
- 一条状态（`panelOpen`）只有一个出口（`setPanelOpen`），徽章、命令、自动化三条路径都走它，
  不会出现"徽章说开着、面板却关着"。

**代价**：

- 点击徽章不再切换开关，老用户的第一下会"扑空"，只能靠 tooltip 与面板里的开关引导（已写进 tooltip）。
- 徽章变成了"要点击才能看到状态"的入口，扫一眼只能看出"有没有在学"，看不出是哪一种——
  这是拿掉两段文字的直接代价。
- `showBadge` 关掉之后页面上没有常驻入口，只能靠 `/thrive panel`。
- 面板不再有"只留标题栏"的省地方形态：需要腾出聊天区就只能整块收起。

## ADR-030 · 界面按块拆进 `ui/`，刷新走登记表而不是互相 import

**背景**：`src/ui.js` 涨到 2582 行，里面同时住着设置页、状态徽章、浮动面板。
改一个设置项的说明要通读两千行，改面板要先跳过一堆设置绑定——两件事明明互不相干。

**决策**：

- **一块界面一个文件**：`ui/settings.js`（settings.html 的绑定与回填）、`ui/panel.js`（重绘 / 交互 / 模式开关）、
  `ui/panel-layout.js`（位置 / 尺寸 / 透明度 / 拖拽）、`ui/badge.js`、`ui/status.js`；
  共用件在 `ui/shared.js`，刷新编排在 `ui/refresh.js`。`src/ui.js` 退成门面，只重新导出
  `index.js` 与回归脚本用到的那几个名字。
- **界面之间不互相 import 具体模块**：谁需要在"状态变了"时刷自己，就把刷新函数登记到
  `refresh.js` 的 `SURFACES`（controls / diagnostics / status / passiveHint / books / badge / panel），
  `refreshUI` 按下表逐个刷，`view` 对象统一传（`{ ctx, settings, available, diag }`）。
- **共享可变状态只留一个**：面板开合状态放 `ui/shared.js`，读 `isPanelOpen()`、写 `markPanelOpen()`；
  "改状态 + 刷界面"的出口只有 `refresh.js` 的 `setPanelOpen`。
- **徽章不调面板**：点击发 `PANEL_TOGGLE_EVENT`，由 `panel.js` 接（沿用 `events.js` 已有的事件解耦）。
- 纯判定 `hasAnyModule` 挪到 `store.js`：设置页、徽章、面板、状态摘要都要用它，
  放在任何一处界面文件里都会让其余几处反向依赖那一处。

**理由**：

- 拆之前设置页与面板是**双向**依赖：设置页的绑定改完要 `refreshUI`（顺带刷面板），
  面板里的布局滑块与「现在触发一次」要回写设置页。直接 import 必然成环——ESM 环能跑，
  但读的人得先在脑子里把环捋直。
- 登记表让 `refresh.js` 变成**完全的叶子**：它不 import 任何界面模块，所以任何界面模块都能放心
  import 它。加一块界面只改两处（自己的文件 + 一个键），不用动别人的参数表。
- 面板几何单独成文件，是因为设置页的滑块与面板自己都要动它；两条路径共用一个
  `applyPanelLayout` 出口，避免"拖动改了 left、滑块改了 width，谁也不知道该以谁为准"。

**后果 / 代价**：

- 读代码要在 8 个文件之间跳；`refreshUI` 具体刷了什么，得看登记表而不是顺着调用栈。
- 登记表按字符串键匹配，拼错只会 `console.warn` 一句，那块界面就不刷新了（已加告警）。
- `src/ui.js` 仍导出 `refreshPanel` 这类内部入口，纯粹是为了 `.workbuddy/` 下的回归脚本不用改；
  业务代码不该用它。
- 四个回归脚本原先按 `src/ui.js` 的源码文本做断言（compact / limits），已改成扫整层
  `src/ui.js + src/ui/*.js`，以后再挪文件不会失效。

## ADR-031 · 学习块按运行模式拆段，注入时拼起来

**背景**：主动与被动是两种态度——常开时该像学生一样逢话必记，借来一轮时该少动工具、只捡关键的。
原来只有一段 `blockText`，两种模式共用，想让被动"少记"就只能整体改掉，主动也跟着变哑。
用户提出给被动单独一份提示词。

**决策**：

- 拆成 `blockCommon` / `blockActive` / `blockPassive` 三个设置键与三段默认文本，注入时按
  「通用 + 当前模式段」拼（`composeBlockText()`），模式段在后。
- 模式判定统一在 `store.getLearningMode()`：主动开着就是 `active`，否则有待学记号就是 `passive`，
  都没有返回 `null`。`isLearningActive` 改成它的布尔投影——注入与工具注册仍然只有一个判据。
- **主动优先**：主动与待学记号重合时按主动走。这不是新规则，而是把
  "主动开着时被动不触发 / 打开主动会丢掉记号" 的同一条结论补上一条读侧保证。
- 「留空 = 用默认文本」的约定三段通用；老 `blockText` 在 `ensureSettings` 里一次性搬进通用段并删键。

**理由**：

- 通用的部分（工具层与正文层分工、写到哪里、怎么写、规则）与"这轮记多少"无关，两种模式都需要，
  复制两份必然漂移；模式差异只占两三行，正好单独放。
- 顺序把模式段放后面，**重合时以模式段为准**在语言层面就成立了（模型读到的最后一句是它），
  不需要做文本去重——去重既判不出"哪句算重合"，也会擅自改用户写的话。
- 判定收在 store 而不是 prompt：`passive.js` 的触发逻辑、工具门控、注入三处都依赖"现在算哪种状态"，
  各判一套迟早出现"块拼的是主动、门控当被动"。

**后果 / 代价**：

- 设置页从 1 个输入框变成 3 个，另加一行「当前生效：通用 + 主动，约 524 字」把拼出来的结果说出来——
  不然用户看着三个框不知道实际发出去的是什么。
- 默认文本变短（680 → 约 520）：原来那段把"积极"和"规则"混在一起，拆开后各自只说自己的事。
- 想彻底去掉某个模式段做不到（留空 = 用默认）。要"只带通用"得等真有人需要时再加开关，
  现在加只会多两个复选框和一条"三个都空会怎样"的边界。
- 老用户的 `blockText` 会被搬走：如果他们本来就按"被动要克制"改过那段，这个语义会落到通用段上，
  影响主动。一次性的、可解释的偏差，比留两套键长期并存的歧义划算。

## ADR-032 · 工具按写入意图拆开，不再保留 upsert

**背景**：v0.18 只有四个工具，`lore_write` 以标题为键 upsert，`desc_write` 用 `mode=append|rewrite`
在一个调用里表达两件事。结果有三种反复出现的失误：标题打错一个字就静默多一条重复条目；
模型为了追加一段不得不重写全文，把没读到过的后半段冲掉；描述和条目都只能"整段提交"，
压缩一次就要把整条正文过一遍。

**决策**：

- 拆成十个工具，命名 `<目标>_<动词>`，动词只有 read / list / add / append / replace / rewrite。
- `lore_add` 与 `lore_rewrite` 分开：标题已存在时 `add` 返回 `TITLE_EXISTS`，`rewrite` 找不到时
  返回 `NOT_FOUND`，两者都不再"顺手新建"。
- 两个 `rewrite` **只改正文**：标题、关键词、触发方式一律保留（沿用 ADR-008 / ADR-015）。
- 新增 `lore_list`：目录只给已启用条目的标题。它虽然也是"读"，但不叫 `read`——
  名字里看不出 list 的能力，模型就会拿它去找正文。

**理由**：

- 一个工具回答一个问题，守卫才能按"它到底看到了多少"精确放行（见 ADR-033）。
  合并的工具必然要在一个调用里同时决定目标、动作和内容，错一步就是一次内容事故。
- upsert 的隐含语义对模型是不可见的：它以为自己"改了一条"，实际新建了一条。
  拆开之后这个歧义由返回值直接说出来。
- rewrite 只动正文，让"压缩"变成一个纯粹的长度问题，不会顺带改掉触发方式。

**后果 / 代价**：

- 工具定义从 4 份涨到 10 份，静态前缀多约 700 token（可缓存，一次写多次命中）。
  换来的是单次调用载荷从 1000–3000 字降到 100–300 字：条目多、描述长时是净赚，短对话里是净亏。
- 模型要多走一步：新建前先 `lore_list`。这一步本身就是防重复条目的机制，
  省掉它等于把"书里有没有"这件事重新交给模型猜。

## ADR-033 · 先读后写分四级，局部编辑不要求读全文

**背景**：v0.18 的守卫只有"读过这个目标没有"一档，于是所有写入都得先读全文。
这既是上下文浪费，也逼着模型在追加时重写整条——而它手里往往只有半截文本。

**决策**：按写入的破坏性分四级，`reads` 里用不同的键表达（键表见 `store.js`）：

| 级别 | 获得方式 | 授权 |
|---|---|---|
| 目录 | `lore_list` 返回过 | `lore_add` |
| 见过标题 | 标题出现在目录里，或 `lore_read` 命中了它 | `lore_append` |
| 预读命中 | 同一个 pattern（含 flags）在 `*_read` 里命中过 | `*_replace` |
| 读过全文 | `*_read` 不带 pattern 且未被截断 | `*_rewrite` |

- 局部编辑**不做 STALE_READ 阻断**：append / replace 的基准是插件刚从盘上读到的完整正文，
  模型提供的是增量，不存在"拿旧版盖新版"。
- 写入成功后作废该目标上所有 pattern 预读（正文变了，之前看清的命中位置不再成立）。

**理由**：

- 追加和替换的安全性由**合成位置**决定，不由"模型看没看过全文"决定。插件在完整正文上做增量，
  模型手里那半截文本物理上冲不掉后半段。
- 反过来，整段覆盖必须知道被覆盖的是什么——这一档不能松。
- 匹配级登记把"替换前先看一眼"变成机制而不是叮嘱：模型必须先用同一个 pattern 读一次，
  才能拿到替换的许可。这比在提示词里写"请先确认"可靠得多。

**后果 / 代价**：

- `reads` 从两类键变成七类，`store.js` 里的键表成了必须读的文档。
- 同一轮里连续替换同一处，第二次会因 pattern 登记被作废而要求重读。这是有意的：
  内容已经变了，旧的命中位置不再可信。

## ADR-034 · 正则替换的安全阀：命中数说了算

**背景**：给模型正则替换能力，最大的风险不是语法错，而是"它以为改了一处，实际改了七处"
或者"一处都没命中，却报告成功"。

**决策**：替换一律先数命中数，再决定做不做（`src/regex.js`）：

- 0 处 → `NO_MATCH`，内容不动，返回"先带同样的 pattern 读一次"。
- 多处且 `replace_all=false` → `AMBIGUOUS_MATCH`，附前 3 处片段，要求细化 pattern 或显式全改。
- 多处且 `replace_all=true` → 执行，返回实际替换数。
- 正则本身超过 `patternMaxChars` → `PATTERN_TOO_LONG`；编译失败 → `INVALID_REGEX` 带引擎原文。
- 替换后正文为空 → `EMPTY_CONTENT`（保住 ADR-009，也防"替换成空串"变相删除条目）。
- `g` 标志不允许模型传，全局与否只由 `replace_all` 表达——两个开关控制同一件事，模型总会用错一个。

**理由**：

- 模型无法可靠地预测自己的正则会命中几处；让它"先想清楚"是在要求它做它做不到的事。
  插件能精确算出来，就应该由插件算，并把结果作为拒绝或放行的依据。
- 返回值里带一段替换后的 `sample`，模型能自己核对改对了没有，不依赖二次读取。

**后果 / 代价**：

- 多匹配场景会多一次往返（模型要么细化 pattern，要么补 `replace_all`）。
- 计数有 2000 次迭代上限：真撞上说明正则写坏了，不是内容太长。

## ADR-035 · 面板几何一律按"视口里实际剩下多少"算，而不是按常量估

**背景**：面板原先的位置是 `right: 16px; bottom: 88px`，宽度 `min(480px, 92vw)`，
高度上限 `min(620px, 100vh - 24px)`。三处都是照桌面端估的常量，在竖屏手机上互相打架：

- 底边让出 88px 是照着"发送区大约这么高"定的。竖屏时输入框折行、按钮换行，发送区轻易
  超过 88px，面板底边就压在输入框上。
- 高度上限只减了 24px，和底边那个 88px 无关。默认 620px 的面板在 700px 高的视口里
  顶边落在 -8px——标题栏（含「收起」）整个跑到屏幕外，看起来是"面板错位叠在页面顶部"。
- 拖过的位置按屏幕坐标存。横屏拖到右下角、转成竖屏后，`panelY` 还在底部，旧代码用
  `innerHeight - rect.height` 夹取，一旦 `rect.height` 本身高过视口，`maxTop` 塌成 8px，
  面板下半截挂到屏幕外。

**决策**：几何全部在 `ui/panel-layout.js` 里按当前视口现算，只有 `applyPanelLayout` 一个出口。

- 宽度：`min(设置值, 视口宽 - 2 × 8px)`，写成行内像素。面板改 `box-sizing: border-box`，
  让"设置里的 480"就是看到的宽度——否则内边距与边框会让夹取刚好越界。
- 未拖动：先量发送区（`#send_form`）的实际高度得到 `gap`，再令
  `maxHeight = min(设置值, 视口高 - gap - 8px)`。顶边因此永远 ≥ 8px。
  量到的 `gap` 超过视口 40% 或发送区不在视口里时回落 88px——宁可少让一点，也不要把
  面板压成一条缝。
- 拖动过的坐标：先夹进视口（左右、上下），**再**按新顶边重算 `maxHeight`。顺序不能反：
  反过来会"坐标夹进来了、高度还是旧的大值"。
- 视口事件（`resize` / `orientationchange` / `visualViewport.resize`）都触发重摆，
  合并在一次 60~150ms 的定时器里。重摆只改行内样式、**不回写设置**：转回横屏时用户
  应该回到他自己拖的位置，而不是被上一次竖屏的夹取结果顶掉。

**理由**：

- 常量估不出来"发送区多高"——它随输入行数、按钮换行、语言而变。能测就别猜。
- 面板是 `absolute` 定位在初始包含块里（不能用 fixed，见 `.thrive-panel` 的注释），
  所以坐标口径只能是 `innerWidth/innerHeight`；`visualViewport` 只用来触发重摆，
  不参与坐标计算，免得两套口径混用后越修越偏。
- 不回写设置是"记住位置"这个需求的底线：夹取是显示层的妥协，不该变成用户的新位置。

**后果 / 代价**：

- 每次重绘多一次 `#send_form` 的 `getBoundingClientRect`（一次强制重排）。面板一天也
  重绘不了几次，可忽略。
- 竖屏且发送区很高时，面板可能只剩 160px 高（`PANEL_MIN_VISIBLE`），内容要滚动。
  这是有意的下限：至少标题栏与「收起」要够得着。

## ADR-036 · 面板按钮按"落点"命名，而不是按动作的语气命名

**背景**：描述写入成功后，面板上同时可能出现三个按钮：`刷新编辑框` / `重新写入` / `关闭`。
用户的实际提问是"刷新编辑框和重新写入有什么区别？关闭又是指关闭什么？"——三个名字里
两个都在"写"，却没说是写到哪儿；"关闭"更没说是关面板还是关这条记录（而它其实是
"把这条记录从面板上收掉，内容不动"）。

**决策**：按钮名里带上**落点**，动作本身由 title 与按钮下那句小字补完：

| 按钮 | 落点 | 覆盖什么 |
|---|---|---|
| 填入编辑框 | 角色编辑面板的文本框 | 框里的文字；不动角色卡，保存才生效 |
| 重写角色卡 | 角色卡（磁盘） | 卡上现版；覆盖前先进「上一版」快照 |
| 移除记录 | 面板里的这条记录 | 无 |

- `关闭` → `移除记录`：它调的是 `discardPatch`，只把 patch 记录置空。
- 待确认 / 冲突两个状态一起改：`接受` → `写入角色卡`，`拒绝` → `丢弃改动`，
  `强制覆盖` 保留（它本来就说清了是"覆盖"）。toast 与确认弹窗里的对应说法一并改掉。
- 次要动作（`丢弃改动` / `移除记录`）用 `--ghost` 压暗，和"会覆盖内容"的按钮分开。

**理由**：

- 这三个按钮的差异不是程度差异（都不可撤销、都有确认），而是**目标对象**不同。
  目标写在名字里，用户不需要先读说明再反推。
- 反向命名（按语气：接受 / 拒绝 / 关闭）要求用户先建立"谁在接受谁"的映射，
  而面板本身就是那个"谁"——最容易混淆的部分被藏起来了。

**后果 / 代价**：

- 文案变长，窄屏上三个按钮会换行到第二行。已写入状态最多三个按钮，不打算为了省一行
  再把它们塞进下拉菜单里——那等于把"说不清"换成"看不见"。
- 文档、toast、设置页里的旧说法（接受 / 拒绝 / 刷新编辑框 / 重新写入）需要同步，
  漏一处就会出现"提示让我点一个不存在的按钮"。
