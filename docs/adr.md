# ADR · Thrive 学习模式

只记录**方向性**决策：定下来的原则、被否决的路线、以及不写下来就会再踩一遍的坑。
具体实现（某个类怎么写、某个样式为什么是 12px）读代码。编号沿用原序，标「并入」的是被合并进来的旧条目，旧编号不再单独成条。

状态：`已定` / `待验证`

---

## ADR-001 · 开关靠工具注册门控，注入落对话尾部（并入 002、003）

**决策**：始终注册全部工具，用 `shouldRegister` 每请求判断，不在生成流程里分支。学习块默认 `IN_CHAT` depth 0（尾部），可改头部或不注入；注入前自己 `substituteParams`。

**理由**：

- 工具表为空时 ST 请求体里连 `tools` 键都没有——关闭态才能与原生逐字节一致。
- `tools` 与 system 前缀都在请求头部，内容或顺序一变，缓存从第一个 token 起失效。落尾部让"开关"只是一次末尾增减。
- ST 两条注入路径对宏的处理不一致（头部走 `preparePrompt`，尾部走 `getExtensionPrompt`），只能自己替换。

**代价**：尾部件每轮重新计费（约 500 token），换来开关便宜。长会话、极少开关的用户可自行改头部。

## ADR-004 · 知识只落原生通道

**决策**：学习成果 100% 写进世界书与角色卡。插件不持有索引、摘要、向量，唯一的插件侧状态是操作性的（本轮读过什么、一份待确认 patch、上一版快照）。

**理由**：模式与原版对话彻底解耦——关闭或卸载插件，学过的东西照样生效。这是特性，不是残留。

---

## ADR-005 · 世界书即时写，只有角色描述走 patch（并入 006）

**决策**：世界书写入立即落盘；只有角色描述暂存成 patch。patch 表达的是"磁盘 vs 暂存"的**单一 diff**，不是操作流水。

**理由**：

- 条目是否进 prompt 取决于关键词命中，改动常常不碰前缀，暂存换不来缓存收益。
- 描述相反：它每轮都在 system 前缀里，合并成一笔才值钱。
- 多份补丁会链式失效（前一条被丢弃，后一条的基准就没了）；用户想看的是"现在会变成什么样"，不是"模型按了哪几下"。

**代价**：世界书没有撤销栈之外的保护；patch 只能整体接受或拒绝，不能逐条挑。

---

## ADR-007 · 先读后写分四级 + 内容哈希，自写视为已读（并入 033）

**决策**：

- 用户每发一条消息清空 `reads`，其后的全部工具调用算同一轮。
- 四级授权：目录 → `add`；见过标题 → `append`；同 pattern 预读命中 → `replace`；读过全文 → `rewrite`。破坏性越大，要求的"看得越多"。
- 读时记哈希，写时对不上 → `STALE_READ`；插件自己写完立刻登记新哈希，否则同一轮第二笔写会被自己挡住。
- 局部编辑**不做** `STALE_READ`：append / replace 在盘上完整正文上做增量，模型给的是增量。

**理由**：追加与替换的安全性由**合成位置**决定，不由"看没看过全文"决定——插件在完整正文上做增量，模型手里那半截文本物理上冲不掉后半段。整段覆盖则必须知道被覆盖的是什么。匹配级登记把"替换前先看一眼"变成机制，而不是在提示词里叮嘱。

**代价**：`reads` 有七类键；同一轮连续替换同一处要重读。

## ADR-008 · `constant` 锁死 false，新建必须有 1 个关键词（并入 009）

**决策**：模型无权设置 `constant`；`keys` 为空拒绝，`content` 空白拒绝。

**理由**：关键词自由 + 常驻自由 = 上下文预算失控（模型完全有能力把所有条目设成常驻）；`constant` 关掉之后没有关键词的条目是写进黑洞。拒绝空内容顺带堵住"用空内容变相删除"。这两条是正确性要求，不是玩法限制。

---

## ADR-010 · 角色描述不加区域标记

**决策**：不划"学习笔记"区，模型可增删改描述任意内容，但写出来的文字必须像原有人设（无列表、无小标题、不提"记忆"）。

**理由**：使用场景是从零养一个角色，不是改造成熟卡；标记会让文本看起来像机器贴上去的。

**代价**：每次读描述都要返回整段（一两千字）；没有"一键删掉学到的内容"。

---

## ADR-011 · 不提供删除，也不给停用

**理由**：删除是最容易被 prompt injection 利用的能力，收益却极低——用户自己在世界书编辑器里能删。

**后果**：模型写出重复条目只能请用户处理。面板上的「撤销新建」是**用户**的动作，不是工具能力。

---

## ADR-012 · 两个模块独立开关，且不降级

**决策**：模块关闭 = 对应工具不注册（模型看不见）。目标类型与可用模块不符时直接拒绝，绝不自动改道写另一边。两个都关时禁止启用学习模式。

**理由**：偷偷改道会让模块开关形同虚设，用户无法预期内容去了哪。

---

## ADR-013 · 工具日志当轮保留、下一轮移出上下文（并入 014、023）

**决策**：当轮把工具消息改写成一行纯文本（模型靠它写回复）；用户发下一条消息时，删掉更早消息的 `extra.tool_invocations`，让 ST 的 `coreChat` 过滤条件自己把它们排除，`mes` 保留、照常显示。只处理**全部由 Thrive 工具构成**的消息。

**理由**：

- ST 渲染的 `<details>` + JSON 极度费 token，且随对话线性增长；删字段是最小侵入——不改 prompt、不拦事件，直接复用 ST 自己的过滤。
- 混合消息里改写 `mes` 等于替别的扩展决定日志长什么样，删字段更会连带把别人的记录踢出上下文，且用户毫无提示。
- 不用 `stealth`：stealth 调用会让 ST 直接 return，**吞掉这一轮的正文回复**，与"记完还要继续说话"冲突。

**代价**：每次清理在历史中段产生一次缓存断点（一次性）；混装其他工具扩展的那些轮次日志不会变短。

## ADR-015 · 只暴露允许修改的字段

**决策**：角色侧只读写 `description`；`personality` / `scenario` / `first_mes` / `mes_example` 既不写也不读。

**理由**：不返回就不可能被改写。比"在提示词里禁止修改"硬得多——模型连内容都看不到，就不会起"顺手调下性格"的念头。

---

## ADR-016 · 直写前留快照，与 patch 开关解耦（并入 022）

**决策**：直写前把当前值存进快照——描述 1 版、世界书按条目 10 条——面板提供"恢复上一版"。**同一条记录兼任两职**：既是恢复用的快照，又是面板「已写入」列表的一行，`action` 决定恢复语义（`created` = 删除，`rewritten` = 写回）。

**理由**：这是手滑保险，不是版本控制，不阻止任何写入。两份数据必然不同步（流水比快照长就要在 UI 里解释"这条不能恢复"，用户看不出差别）。

---

## ADR-018 · 读范围与写范围分离（并入 017）

**决策**：写永远只作用于用户选的那一本；读可放宽到"当前角色绑定的所有书"，由设置决定，返回值必须带来源书名。

**换书不拦截**：`lore_read` 发现书变了就返回一句"书已切换，不要重复记录"。不提醒的话模型会以为自己忘光了，把旧内容原样重写一遍。

**理由**：放宽读范围不增加写入面；不返回书名，模型改写时会写错书。

---

## ADR-020 · 能不能用一律问 ST（并入 024）

**决策**：只调 `ctx.isToolCallingSupported()`。为 false 时禁止开启（徽章置灰，只报第一条原因）；已开启的对话**不自动关闭**——模型与后端是随时会变的环境，模块开关才是用户的稳定配置。

**理由**：1.19 起按来源分别检查模型能力（OpenRouter 看 `supported_parameters`、Mistral 看 `capabilities`、Fireworks 看 `supports_tools`……），后处理改成只认带 `_tools` 后缀的白名单，还有走 Responses API 的特例。插件做第二份实现必然失真，ST 加一个来源就错一次。

**后果**：诊断只能给"为什么不行 + 去哪改"，无法穷举组合。这是有意的。

---

## ADR-021 · 不自动激活可写书

**决策**：插件不碰激活列表，改为三处如实说明：`lore_read` 的 note、写入返回的 note、面板的警告。

**理由**：

- `selected_world_info` 没有公开 API。唯一可行的做法是改 `#world_info` 的 value 再 `trigger('change')`——等于替用户做一次他不知情的设置变更，而且依赖 DOM 结构，ST 改版就碎。
- 激活哪几本书是用户的**世界观边界**，多激活一本就可能让别的角色带上不该有的设定。
- 但"不激活却写进去"是看起来成功、实际无效，比拒绝更糟。所以"说清楚"是必须的，不是可选的。

**代价**：用户第一次用要自己勾一次书；模型被要求提醒用户，会多出半句台词。

---

## ADR-025 · 被动学习只"借"一轮

**决策**：一个一次性记号 `pending`，`isLearningActive() = enabled || pending`，注入与工具注册都只认它。结算点选在角色消息落盘，不是生成结束（后者点停止也会发，扣掉记号等于白借一次）。同一轮记下用户消息哈希，避免角色复述关键词连开两轮。

**理由**：**不改用户的状态**——用 `enabled` 开开关就得自己负责关，中途报错、切对话、刷新都会留下"自己亮起来的学习模式"；记号是可丢的，读不到就是没有。一个判据两个出口，才不会出现"块进去了、工具没注册"的半开状态（这类不一致最后都表现为"模型不听话"，最难查）。

---

## ADR-026 · 写完立刻刷新 ST 的编辑器

**决策**：写入成功后，若编辑器正开着这个目标就把它刷到最新——描述只覆盖**没被用户改过**的输入框；世界书整块重绘，并还原搜索词、页码、抽屉与滚动位置。

**理由**：ST 编辑器手里是快照不是引用（角色卡提交整张表单，世界书 `loadWorldInfo` 返回深拷贝），用户在编辑器里动一下旧内容就整块盖回去，而世界书盖的是**整本书**。靠「再写一次」解决不了，"提醒用户关面板"等于把问题推给人。

**代价**：重绘后输入焦点回不去；写入与用户按键撞在同一毫秒的窗口没被消除。

---

## ADR-027 · 数值上限集中定义，读时夹取（并入 019）

**决策**：`src/limits.js` 是唯一定义处（默认值、范围、步进），设置页的 min/max/step 也从这里灌进 DOM。读取时夹取：0 / 空 / 非数字 / 超范围一律回落默认，软提醒按硬上限封顶。

**理由**：这些数字直接决定"这次写入被拒还是通过"。`Number(x) || 常量` 对 0 失效、对负数会让 `> hardLimit` 永远成立；软 > 硬是无意义的组合（内容在被拒之前根本收不到提醒）；范围若与夹取分开维护，迟早出现"输入框允许 5000、实际夹到 2000"。

**附：不做每轮写入配额**——ST 的递归上限 5 已是天然约束，额外配额属于"非必要硬限制"。

---

## ADR-029 · 徽章退成面板开关，面板只放这一场的东西（并入 035、036）

**背景**：徽章原是「主动｜被动」的文字胶囊，横在输入框旁：占地方、尺寸与旁边固定大小的图标不一致、还会被 flex 容器拉伸。

**决策**：

- 徽章缩成一颗固定尺寸图标，**只开关面板**；状态用图标本身表达（强调色 = 主动开着、掺正文色 = 只有被动、待学呼吸、右上角计数）。
- 开关搬进面板第一段，每个开关配一句"它管什么"；整块可点，切换**不弹 toast**——状态就写在被点的那块上。
- 按钮按**落点**命名（`填入编辑框` / `重写角色卡` / `移除记录`），不按语气（接受 / 拒绝 / 关闭）。
- 几何按视口现算：量发送区实际高度反推高度上限，拖过的坐标先夹进视口再算高度；重摆不回写设置。

**理由**：35px 的方块里塞两段文字怎么放都比旁边图标"外来"；三个按钮的差异不是程度而是**目标对象**不同，按语气命名会逼用户先建立"谁在接受谁"的映射；常量估不出"发送区多高"（它随输入行数、按钮换行、语言而变），能测就别猜。

**代价**：点徽章不再切开关，老用户第一下会扑空；窄屏按钮会换行；夹取是显示层的妥协，不能变成用户的新位置。

---

## ADR-030 · 界面按块拆进 `ui/`，刷新走登记表

**决策**：一块界面一个文件，设置页再按组拆成一堆小文件。谁要在状态变化时刷自己，就把刷新函数登记到 `refresh.js` 的 `SURFACES`，`refreshUI` 逐块刷；界面之间不互相 import；共享可变状态（面板开合）只留一个出口。

**理由**：设置页与面板原本双向依赖，直接 import 必成环——ESM 环能跑，但读的人得先在脑子里把环捋直。登记表让 `refresh.js` 变成完全的叶子，任何界面模块都能放心 import；加一块界面只改两处（自己的文件 + 一个键）。

**代价**：读代码要在多个文件间跳；登记表按字符串键匹配，拼错只 warn 一句，那块界面就不刷了。

## ADR-031 · 学习块按运行模式拆段

**决策**：`blockCommon` / `blockActive` / `blockPassive` 三段，注入时按「通用 + 当前模式段」拼，模式段在后。模式判定收在 `store.getLearningMode()`，主动优先。空串 = 用默认文本；老 `blockText` 一次性搬进通用段。

**理由**：通用部分（写到哪、怎么写、规则）与"这轮记多少"无关，复制两份必然漂移。模式段放后面，**"重合时以模式段为准"在语言层面就成立了**（模型读到的最后一句是它），不需要做文本去重——去重既判不出哪句算重合，也会擅自改用户写的话。

---

## ADR-032 · 工具按写入意图拆开，不保留 upsert

**决策**：十个工具，命名 `<目标>_<动词>`，动词只有 read / list / add / append / replace / rewrite。`add` 与 `rewrite` 分开（标题已存在 → `TITLE_EXISTS`，找不到 → `NOT_FOUND`，都不再"顺手新建"）。两个 `rewrite` 只改正文。

**理由**：upsert 的隐含语义对模型不可见——它以为改了一条，实际新建了一条；标题错一个字就静默多一条重复条目。合并的工具必须在一个调用里同时决定目标、动作和内容，错一步就是一次内容事故。`rewrite` 只动正文，让"压缩"退化成纯长度问题，不会顺带改掉触发方式。

**代价**：工具定义从 4 份涨到 10 份（静态前缀约 +700 token，可缓存），换来单次载荷从上千字降到一两百字。

---

## ADR-034 · 正则替换由插件数命中数决定放行

**决策**：0 处 → `NO_MATCH`；多处且未 `replace_all` → `AMBIGUOUS_MATCH`（附前 3 处）；替换后为空 → `EMPTY_CONTENT`；`g` 标志不让模型传，全局与否只由 `replace_all` 表达。返回值带一段替换后样本，模型能自己核对。

**理由**：模型无法可靠预测自己的正则命中几处，"先想清楚"是在要求它做不到的事。两个开关控制同一件事，模型总会用错一个。

---

## ADR-037 · 工具常驻：把"能不能用"从注册表搬到提示词

**决策**：`toolsResident`（默认关）。开着时 `shouldRegister` 只留结构性条件，此刻能不能调用由 `tool-state.js` 判（不可用返回 `TOOL_UNAVAILABLE`，不进 handler），并靠「工具指令」的 `{{x}}` / `{{!x}}` 宏说明。

**理由**：缓存断点从"请求最前面"后移到 system 中后段，工具定义这块最大的内容才能复用。可用性原本是**隐式**的（看得见 = 能用），常驻之后必须换成**显式**文字，而文字必须跟着状态变——这就是「工具指令」存在的理由。判定收在一处，才不会"提示词说可用、调用却被拒"。

**代价**：常驻一直占 token；模型可能试一次被拒；关掉 `promptInject` 时就只剩"工具在、调用被拒"，所以两个开关放在同一组。

---

## ADR-038 · 提示词用卡片排序 + 一道分界线（并入 039）

**决策**：卡片顺序存 `promptOrder`；「其它提示词」是一张**不注入的分界线卡**，上方进系统提示词区、下方进对话尾部；同组按顺序用空行拼成一段再注入。工具清单直接读 `ToolManager.tools`，不在界面里抄第二份元数据。

**理由**：ST 的扩展提示词只有"相对 main 的前 / 后"两个落点，分界线把这两个落点变成可拖的对象，用户看到的就是"上面 / 下面"本身。同位置多键的合并顺序在两条路径上不一致（文本补全按 key 排序，聊天补全按插入顺序），拼成一段就不用赌。界面上写的工具描述必须等于请求里发的那份，抄一份等于给自己埋一个手动同步的坑。

**代价**："模式段在后"不再由代码保证，改由用户顺序决定；`other` 一侧只能保证"main 之后、其余预设之前"，插不进预设中间。

---

## ADR-040 · 压缩从模型侧搬到用户侧

**决策**：取消自动压缩——软提醒不再出现在任何工具返回里，`over_limit` 一并去掉；软提醒降级为筛选条件，只服务一条独立侧栏（贴窗口左边、不可拖动）；硬上限照旧拒绝写入，模型侧只剩这一条规则。

**理由**：压缩那一刻模型拿不到对话上下文与用户意图，压掉的往往正是刚讲完、还没用上的细节；触发由"长度"而非"需要"决定；而且用户看不见发生过什么。硬上限必须留着——它是**可见的**拒绝，模型能收到错误、用户能在日志里看到，不像悄悄压缩那样无声无息。

**代价**：用户多一步手动操作（靠入口高亮、新增条目时闪一下、徽章 tooltip 让它显眼，但不自动弹窗——压缩是低频动作，弹窗只会变成噪音）；扫描每次要读一遍世界书，全部去抖。

## ADR-041 · 设置页：解释收进「?」，小字只报状态（并入 028）

**决策**：标签右侧一颗「?」，点开是**行内**说明（不是弹层）。可见小字只写"现在是什么状态、哪里不对"，一切正常时不写任何字。分组按"装完要不要先调一遍"合并，默认全收起（复用 ST 原生 `.inline-drawer`，嵌套天然可用）。

**理由**：设置页是用来改开关的，不是读文档的。原来状态与解释混在一起（"已关闭：模型看不到世界书工具，学习块里相关段落建议一并删掉"里既有可据以行动的状态，又有看一次就够的背景），三段文字并排就是一堵墙。异常态才需要人处理，所以默认状态整页是安静的。

**代价**：说明默认不可见，新用户可能没注意到那颗「?」——靠 title、手型指针、以及异常小字仍然外显来兜底。

## ADR-042 · 角色描述可以存进世界书：一条常驻保留条目

**决策**：`descStorage` = `card` / `worldbook`。后者把描述写在**与角色同名那本世界书**的 `【角色描述】` 条目里，必须常驻且启用；`desc_*` 四个工具名字、参数、守卫全不变，只换落点；`lore_*` 六个工具看不到也改不了它（`RESERVED_ENTRY`）；该模式不做 patch、不做 diff；切换**不迁移内容**，切回 `card` 时把条目停用。

**理由**：

- 两套存储的成本不在写入，而在**每个功能都要适配两遍**：上限怎么算、失败怎么回滚、面板怎么显示、压缩面板怎么编辑、快照存哪儿。
- 世界书本来就有编辑器、激活机制与快照体系，再造一份存储等于把同一件事做第二遍；常驻条目天然满足"每轮都在场"。
- 固定名 + 全角括号：条目标题是插件唯一的定位键，名字必须稳定，且不像人手会写的东西。
- 按角色分书：`writableBook` 是全局一份，多角色共用会互相覆盖；"这本书就是这个角色"是用户本来就有的心智模型。
- `desc_*` 保留而不让 `lore_*` 直接管：同一条内容有两个工具入口正是这次要消掉的复杂度；而四级守卫在描述路径上依然成立。
- 不迁移：要判断"卡上的描述和条目里的内容哪个更新"，两边都可能被改过，不如从空白开始让用户明确决定。

**代价**：常驻 = 每次改写都动前缀缓存，这是"每轮在场"的必然代价。同名角色会共用一条，后写覆盖前一个。

## ADR-043 · 界面按作用域分两处：面板管这一场，设置页管所有对话

**决策**：判据只有一句——**换一场对话，它该不该变？** 该变 → 浮动面板，不该变 → 设置页。设置页不再有「当前对话」状态行、不随对话变化。

**理由**：作用域是唯一的信任线。用**位置**表达比用文案可靠：小字会被略过，挪走不会——加标签等于承认"位置说不清"，那就等于没有分区。设置页从此是"同一副样子"，这句话可以被验证。

**代价**：想开被动或换书都得先把面板叫出来；设置页里找不到的东西，得知道去面板找。

## ADR-044 · 可写书、描述存储、被动开关按对话记

**决策**：三项下沉到 `chat_metadata`，全局只留初值（`enabledByDefault` / `passiveByDefault`）。`worldbook` 模式下可写书由 `getWritableBook` 一处钉死，不看设置里的值。迁移按"初值"处理：旧全局键留到用户在某场对话里真正选过一次。

**理由**：作用域应由**数据本身的含义**决定，而不由当初写在哪个文件决定——这三项都在回答"这一场的内容写到哪"。一处收口比两处对齐可靠：钉死之后不是"记得同步一下"，而是根本读不到别的值。迁移读旧值而不是只搬一次：升级时用户可能开着十几场对话，只有一场拿到旧值，其余会表现成"插件把我的书弄丢了"。

**代价**：旧全局键残留一段时间；"以后新对话都开被动"要在设置页改，"现在这场"要在面板点。

## ADR-045 · 判据回设置页、落点进面板

**背景**：ADR-044 决策 5 给设置页开了个口子——落点原地留着加一枚「对话」标签，同时把全局的被动判据留在了面板里。两处都违背 ADR-043：标签是用文案表达作用域；面板里混着两种作用域，360px 的小窗没地方写标签，用户只能靠「?」里的长文去分辨。

**决策**：描述存哪儿与可写书搬进面板「更多设置」；被动判据搬回设置页新开的「被动学习」组。设置页从此没有任何随对话变化的控件。

**理由**：面板里只剩一种作用域，第二行小字就可以安心只写状态（`本对话` / `还差 3 条`）——混着两种时每块都得留一行解释自己是哪种。落点搬进面板后，"这一场写哪"（模式 → 落点 → 待确认 → 记录）落在同一条竖线上，自上而下就是一次写入的生命周期。

**代价**：换书必须先把面板叫出来；面板「更多设置」在 360px 下要滚动才能看到「现在触发一次」。

## ADR-046 · 删掉「写入模块 / 暂存 / 读范围」三个开关：能力由存储模式决定

**决策**：设置页不再有「写入模块」（世界书 / 角色描述两个勾）、「描述改动先暂存」、「读取范围」；四个设置键（`moduleWorldbook` / `moduleDescription` / `patchEnabled` / `readScope`）在 `ensureSettings` 里直接删掉，旧值不迁移。能力只剩一条规则，由 `descStorage` 决定：

| | `card` | `worldbook` |
|---|---|---|
| 写世界书 | 可（那本书） | 可（角色同名书，`getWritableBook` 钉死） |
| 写描述 | 可，恒先暂存成 patch | 可，直接写 `【角色描述】` 条目，没有暂存 |
| 读 | 只读可写书 | 只读角色同名书 |

「这本书没激活」只说一句话：去「世界书」面板勾选它。面板不再报角色卡上残留多少字。

**理由**：

- 三个开关里没有一个是"两边都成立"的：暂存在 `worldbook` 模式没有意义，另外两个在两种模式下都该是同一个值。可调的默认值不是自由度，是"调了没反应"的旋钮。
- 它们能把状态调成不存在的形状——两个模块都关（整个插件空转）、只关描述而描述又存在书里。为此要写"模块全关时禁止启用""关模块不清理内容"这类补丁规则，而这些规则本身没有人会主动去看。
- 读范围放宽的收益（少录一遍设定）小于代价：模型读到一条改不了的内容，无法判断它是"已经记在别处"还是"还不存在"，两个答案都会让它做错事。收成一本之后，读到 = 能改。
- 能力归属由**落点**表达比由**开关**表达可靠：描述存进书里，它就是书里的一条；不需要用户再记住"这个勾现在管不管用"。
- 面板那条"角色卡上还留着 N 字"同理：它描述的是切换模式的残留，用户既不知道该怎么处理，也不影响本模式读写。未激活那句只说"去哪开"。

**代价**：想"只记世界书、别动描述"的用户没有开关了，只能整体关掉学习模式，或改用 `worldbook` 模式把描述收进书里自己去编辑；描述工具在两种模式下都注册，区分靠落点而不是开关。

## ADR-047 · 世界书改动先落虚拟世界书，用户点保存才写进真实世界书

**背景**：世界书是热路径。一次 `saveWorldInfo` 会让文件变、让 ST 的世界书缓存失效、让位于请求头部的那段内容变——前缀缓存从那一条开始整段重算。而模型写进来的东西大多是"这一轮学到的三句话"，用户要么想改一改，要么根本不想留；现在没有任何环节拦在中间，写错了只能靠「已写入 → 恢复写入前」一条条退回去。

**决策**：在工具与真实世界书之间加一层**虚拟世界书**（缓冲区）。

| | 谁写 | 什么时候生效 |
|---|---|---|
| 虚拟世界书 | 工具（`lore_*` / `desc_*` / 压缩面板"改正文"） | 立刻，但只在插件内部可见 |
| 真实世界书 | 只有用户点「保存到真实世界书」 | 保存之后，ST 下一轮扫描才会带进上下文 |

- **路由只放在两个 IO 入口**（`targets.loadBook` / `targets.persistBook`）：有缓冲区就读写缓冲区，没有就走磁盘。中间那些解析、四级读守卫、长度上限、增量合成、条目模板全都不知道自己在哪一层上工作。
- 缓冲区按对话存在 `chat_metadata.thrive.draft`：整本条目副本 + 开出来那一刻的指纹 + 被工具动过的条目表。
- 保存 = **整本替换**。开出来之后真实世界书若被别处改过（指纹不符），第一次保存会被拒绝，界面把确认文案换成"会覆盖那些改动"再问一次。
- 窗口**只读**：只显示会被记录的参数（标题、关键词与组合方式、正文 diff、常驻 / 停用），两个按钮都是用户的动作。
- 写入快照按**层**记（`layer: disk | draft`）；恢复必须回到当初写入的那一层，跨层一律拒绝。

**理由**：

- 一次写入的代价落在三个地方（文件、编辑器、缓存），而这三处都只有"用户已经同意"才值得付。把同意挪到写入之后，模型这一轮仍然可以自由地追加、替换、整理——它读到的就是缓冲区，跟读真的世界书没有区别。
- 拦截放在 IO 入口而不是工具层：如果每个工具自己判断"写哪儿"，那么"先读后写"的守卫会在两层之间错位（读到磁盘、写到缓冲区），长度上限、关键词截断、`created` / `rewritten` 的语义也要各维护一份。两个入口收口之后，缓冲区对上层是**透明**的，这正是它该有的样子。
- 只读而不是可编辑：能就地改就会有三套真值（模型写的、世界书编辑器写的、你在窗口里手写的），而判重、关键词上限、硬上限这些规则本来只长在写入路径上，搬进界面等于重写一遍且必然漂。要看 diff 的目的本来也只是"决定留不留"。
- 整本替换而不是逐条合并：缓冲区里就是那本书的完整副本，"保存"在用户心里等于"这本书变成这样"。合并语义会引出"哪些条目算我的、哪些算它的"，而缓冲区没有记录这种归属。
- 冲突检测用开出来那一刻的指纹，而不是逐条比对：用户要的是"我改过没有"这一个判断，逐条比对只会在确认框里堆一堆条目名。拒绝一次比默默覆盖安全——覆盖掉的是用户在世界书编辑器里刚敲的字。
- 快照分层是必然的：缓冲区里的 `before` 是"缓冲区里的样子"，保存之后拿它覆盖磁盘等于凭空造出一份没人同意过的内容。

**代价**：

- 同一场对话的聊天文件里多出一份整本书的副本（两百条、每条八百字约 160 KB）。这是"刷新页面不丢改动"的代价——放内存里更轻，但用户按一下 F5 就没了。
- 学到的内容在保存之前**不进上下文**：ST 只扫磁盘上的书。模型自己读得到（走缓冲区），但角色这一轮不会因此记起新设定。这是"先看再落盘"的直接后果，不是 bug。
- 缓冲区开着时，「已写入」里属于真实世界书的旧记录暂时恢复不了（`DRAFT_ACTIVE`）：磁盘被改，缓冲区里那份旧副本看不见，之后一保存又把恢复的内容冲掉。要恢复得先把缓冲区处理掉。
- 换可写书时若有未保存的改动会被拦住，多一步操作。

## ADR-048 · 提示词：独立窗口、自建卡、按角色切段、有损导入预设

**背景**：原来的「提示词」只有一张卡片列表，只能拖位置——想加一条自己的提示词没有入口，想改角色没有入口，想从 ST 预设搬一份进来只能一条条手抄。第 22 步要把它做成真的编辑器。

**决策**：

1. **列表搬进独立窗口**（`#thrive_prompts`，第四个窗口）。设置页折叠块只留两个开关、一行摘要和「打开编辑器」。
2. **加自建提示词**（`customPrompts`）。内置卡不能删、只能停用；自建卡可增删改、可停用、可改角色。落点由列表位置决定，不单独存字段。
3. **按角色切段注入**。一条 ST 扩展提示词只带一个 role，所以相邻同角色的卡拼成一段，段号补零（`thrive_head_000`）。逐段调用 `substituteParams`，`setvar` 的副作用才能被后一段读到。
4. **有损导入 ST 预设**。保留名称 / 正文 / 角色 / 启用状态 / 落点；忽略触发器与 `injection_order`；跳过标记块与空条目并计数；内置卡原样保留。

**理由**：

- 一屏要同时放名称、角色、开关、预览、状态角标，塞进设置页的折叠块只能层层套折叠。而它又是"偶尔整批调一次"的东西，不值得常驻——独立窗口正好。
- 自建卡的落点跟着列表走，而不是存一个 `side` 字段：界面上只有一条竖排列表，"在上面就在系统区"是能看见的事实，存字段等于给同一个事实留两份真值，拖一次就得同步两处。
- 切段是角色能生效的**唯一**办法。不切段的话，混在同一个 value 里的用户 / 助手消息只能全按系统发——那"改角色"就是一句空话。段号补零是因为 ST 按 key 字典序拼接，`_10` 会排到 `_2` 前面。
- 逐段替换而不是先拼成一大段再替换：`{{setvar}}` 是副作用式的，拼完之后 ST 只会从前往后展开一次，中间隔着段边界也照样能读到——但一旦将来某段被跳过（空卡不断点导致的重排），拼好的大段就没法按段回填。让"段的边界"始终等于"替换的边界"，行为才可预测。
- 导入是有损的，而且必须**把有损说清楚**：ST 预设里有一半字段在这个插件里没有对应物（触发器、注入深度、`system_prompt` 标记），静默丢掉会让人以为导进来的东西和原来一样。所以确认框逐项列出"导入几条、跳过几条、几条核心系统提示词可能重复"。
- 导入不动 `promptInject`：那是用户手动关的自动注入，一次导入把它打开属于替用户做主。

**代价**：

- 只支持一份提示词集合，不做多预设的存储与切换。要留旧的就自己备份——这是明确的范围裁剪，不是遗漏。
- 导入后 system 区的内容与人家的预设不会完全一致：标记块没了、触发器没了、顺序按落点重排。想一比一复刻得手动补。
- 段数随顺序变化，改一次顺序可能让 system 前缀变一次，缓存重新 prefill。这是"角色真的生效"换来的。
- 窗口与设置页都要在状态变化时刷新，多一个登记项；窗口内部的草稿 / 拖动状态要自己做，不能靠整块重绘。

**修订（v0.31）——行内只留对齐的两列，重活全交给 ST**：

1. 启用勾选换成**尾部滑块**。左侧复选框和抓手挤在同一侧，行首随之参差不齐；拖到尾部后，每行右侧固定是「编辑 + 滑块」两列。
2. **角色下拉与删除按钮移进编辑区**。角色已经在行上以 chip 显示，再摆一个下拉等于同一件事两个入口；删除是低频破坏性操作，摆在行上只会让右侧列宽不一致。
3. **去掉正文预览行**。省一行，也省掉"预览被截断看不出区别"的困惑——想读正文就展开。
4. **编辑按钮可再点收起**，等同于一个小抽屉。有未保存改动时先确认一次。
5. **全屏编辑与宏补全直接复用 ST**：`callGenericPopup(POPUP_TYPE.TEXT, { wide, large })` 就是 ST 自己的放大编辑；补全只需给输入框挂 `data-macros` / `data-macros-autocomplete="always"`，靠它的 MutationObserver 自己初始化。自己实现一套补全或放大窗，等于把 ST 的宏清单、样式、键盘行为再抄一遍，且必然跟不上版本。
6. **导入多一个来源**：除了挑文件，还可以直接列 ST 现有预设（`getPresetManager('openai')`）。导入逻辑仍然只有一份，来源只是"怎么拿到那段 JSON"。
7. **确认框改用 `callGenericPopup`**。旧的 `#dialogue_popup` 在新主题下会把中文按钮压成竖排（两个字挤成两行），已经 deprecated。
8. **撤掉「生效 / 未生效」角标，改成整行亮暗跟着"启用"走**。角标回答的是"这一轮会不会进请求"，那个答案跟着学习模式、当前轮次、工具常驻一起变；没开学习时一屏几十条全是「未生效」，既没有区分度，又占掉每行一个位置。而"我把它关了没有"是用户自己设的、稳定的事实，用亮度表达最省也最准。原来那句解释没丢，挪到行内小字的 `title` 上——想知道为什么，悬停就有，不需要时完全不占位置。
9. **整体尺寸放大一档**（行高 48→58、滑块 30×16→38×22、按钮最小 30px 高）。这个窗口在手机上也会被点到，而行上最窄的点击目标是滑块与「编辑」——它们原本只有 16px 高。宁可一屏少放两条。

代价：行上的信息变少，判断"这条写了什么"必须展开一次；补全浮层是 ST 的 DOM，重绘 / 关窗时要主动失焦并兜底清理，否则会悬在窗口上。撤掉角标之后，"为什么这条没进请求"需要悬停才看得到——手机上（没有 hover）只能靠模式开关与启用状态自己推。

## ADR-049 · 一次性内部会话：自建消息栈 + 直连传输 + 会话私有工具

**背景**：学习和对话现在共用同一个上下文。后果有三条，都不是"体验问题"而是结构问题：

1. **对话要等学习跑完**。学习挂在 ST 的工具递归里——它出现在回复链中间，用户看到的是"先想很久、然后才回话"，而这两件事本来没有先后关系。
2. **工具调用与对话轮次绑死**。工具消息落在 `mes` 里，于是受后处理模式、消息编辑、回退、`getChat` 的过滤条件、递归上限影响；用户删一条消息就等于动了学习的输入。
3. **提示词互相污染**。学习块进的是这场对话的 system 区，学习用的指令伪装成一条用户发言留在历史里，之后的每一轮都要背着它。

要做到"学习在一个独立会话里跑"，得先有这样的东西：能拿一份自己的预设和消息、发一次带工具的请求、解析回来、执行工具、再发——而且**不碰当前聊天**。ST 没有"会话"这个概念：`ChatCompletion` 是绑定在 `chat` 数组和 `chat_metadata` 上的，`generateQuietPrompt` / `generateRawData` 都把结果往当前 chat 写。

**决策**：会话是插件内部的**内存对象**，五步一条链，每一层都能单独替换、单独验证。

| 步骤 | 函数 | 这一版做什么（stub） |
|---|---|---|
| 开始 | `openSession` | 体检传输、建对象、分配 `id` / scratch / abort 控制器；不计数、不发请求 |
| 填预设 | `applyPreset` | 两段固定文本（system 规则 + assistant 示例）编译成 runs |
| 发消息 | `sendUserMessage` | 追加一句固定指令 |
| 跑循环 | `runLoop` | 请求 → 解析 → 执行工具 → 再请求，直到某个终止条件 |
| 结束 | `closeSession` | 收尾 + 留最后一场供 `/thrive session log` 读；幂等 |

`runSession` 是给斜杠命令用的组合体：五步串起来 + 互斥（`SESSION_BUSY`）+ 唯一一个兜底 `catch`。

**四层边界，各自一条线**：

- **`session-messages.js` 自建消息栈**。四个冻结工厂（`systemText` / `userText` / `assistantReply` / `toolResult`）+ `toChat()` 复刻 ST `getChat()` 的序列化 + `estimateTokens()` + `assertProtocol()`。不复用 `Message` / `MessageCollection`。
- **`session-provider.js` 只认 OpenAI 形状**。`detectShape()` 分流，`readReply()` 出 `{content, toolCalls, finishReason}`；Claude / Gemini / Cohere 直接给 `SESSION_PROVIDER_UNSUPPORTED`，不猜。
- **`session-tools.js` 会话私有工具表**。三个 stub，绕开 `ToolManager`，`executeTool()` 永不抛、返回文本永不为空。
- **`session-transport.js` 是唯一 ST 耦合层**。`createGenerationParameters(settings, model, 'quiet', messages)` 造 payload → 自己 `fetch`；`runLoop` 只认 `deps.request`，不知道 ST 存在。

**复用判据**：**优先复用相对安全、无副作用的，否则自建。** 落到这一版就是——

| 复用 ST | 自建 |
|---|---|
| 设置、模型、连接配置、请求头（`getRequestHeaders`） | 消息数组与其序列化 |
| `createGenerationParameters`（payload 形状） | 请求的发送与超时 |
| `canPerformToolCalls`（能力体检） | 工具表与工具执行 |
| 上下文长度（作预算上限） | 消息预算估算 |

**理由**：

- **为什么自建消息栈，而不是复用 `Message` / `MessageCollection`**：`Message.createAsync` 会走 tokenizer——`countTokensOpenAIAsync` 即使一次给一整个数组也是逐条 POST；还会落 IndexedDB；构造函数标着 `@private`，等于借用别人的内部实现。而 `runLoop` 需要的东西少得多：一个能序列化成 OpenAI 数组的列表，加一个估算。自建的代价是协议正确性变成我们的责任，所以配了 `assertProtocol()` 六条不变式（role 合法 / tool 消息必须有 `tool_call_id` 且能对上一条 assistant 的调用 / assistant 有 `tool_calls` 时 `content` 为 `null` / `arguments` 必须是字符串 / id 不重复 / 内容非空）和一份离线断言脚本。**先写测试再写实现**在这里不是流程洁癖：`assertProtocol` 第一版把 `system` 漏在合法 role 之外，一跑就红了——这种错在真机上表现为"模型莫名其妙不听话"，最难查。
- **为什么不 `sendOpenAIRequest('quiet')`**：那条路会 emit `CHAT_COMPLETION_PROMPT_READY`，而监听者是**所有**扩展，谁都能在我们注入之后改 payload（`messages = messages.filter(...)` 造的是新数组，元素引用原样保留，原地改我们的消息对象是可能的）；它还带 ST 的错误弹窗、发送锁和 `quiet` 分支的全部假设。我们要的是"这段字节只有我能决定"。
- **为什么不挂事件钩子再改 payload**：同一件事的另一种写法。挂上去就得保证每次摘干净、得处理"另一个扩展也挂了且顺序在后"，还得依赖"钩子里改 `messages` 一定会被用上"。直连之后这三件事一起消失：没有钩子、没有摘除、没有顺序。
- **为什么不 `generateQuietPrompt`**：它包的是 ST 的完整生成流程（宏、swipe、清理、写入当前 chat）。我们要的只是"那次 JSON"，不要它的副作用。
- **为什么不 `generateRawData`**：它的形状是"单轮、无工具、结果直接给人看"。要塞工具调用就得改它的返回结构，改完它就不再是"raw data"。
- **为什么不 `ChatCompletionService.processRequest`**：它假设 `messages` 是 `MessageCollection`，并且按 `canPerformToolCalls` 决定写不写 `tools`——而 `quiet` 被明确排除在工具调用之外（`tool-calling.js`），也就是说这条路径**永远不会**替我们写 `tools`。既然工具得自己写，就没有理由再绕它。
- **为什么不 `prepareOpenAIMessages`**：它干的正是"把当前 chat 转成请求消息"，而我们的消息不是 chat。
- **为什么直连还要断言 `payload.type === 'quiet'` 和 `stream === false`**：跳过 ST 的判断之后，光看自己传的参数不够，得看它**造出来的东西**。这是本 ADR 里唯一"依赖 ST 行为"的地方，所以显式断言（失败给 `SESSION_DRIFT`），不假设。
- **为什么工具私有**：`ToolManager` 是全局的，注册即对**所有**请求可见。而"学习的工具不该出现在正常对话里"正是这件事的前提结论——不能一边说解耦、一边把工具塞进全局表。
- **为什么采样只覆盖 payload 里已存在的键**：o1 / gpt-5 那条分支会删掉 `temperature`、把 `max_tokens` 改名。无脑覆盖等于给它们塞一个不认识的字段。只改存在的键，就没有这个分支要维护。
- **为什么超时自己做**：直连之后没有 ST 的队列替我们兜底，一个不回来的请求会把会话永远挂在 `running`。`withTimeout()` 直接 abort fetch，`SESSION_TIMEOUT` 与 `SESSION_ABORTED` 分开，因为一个是"环境不对"、一个是"我叫停的"。
- **为什么用 `sawTools` 单独记一笔**：`stopped: 'no_tool_calls'` 既是"模型干完了"也是"模型根本没理工具"。不区分的话，一场从头到尾没调过工具的会话会被当成成功——这类"沉默的失败"比报错更难发现。
- **为什么撞轮数上限算没跑完**：`SESSION_ROUND_LIMIT` 的文案写的是"结果可能不完整"。终止条件有四种（`no_tool_calls` / `rounds` / `aborted` / `fatal`），只有第一种是正常结束。

**代价**：

- **消息协议的正确性归我们**。`toChat()` 一旦和 ST 的 `getChat()` 漂开，表现是模型收到一份"看起来对但语义不对"的请求。所以留了三样东西：一次性形状比对（`.workbuddy/session-isolation-check.py`，在真实页面里同一份输入走两边、逐字段比）、从真实抓包冻下来的 fixture（`.workbuddy/session-fixtures/payload.json`：请求类型、工具定义、第一条请求的消息、两边的序列化结果），以及离线断言（`.workbuddy/session-check.mjs`，38 条里 5 条是回放 fixture）。**工具定义被无意改动**同样会在这里被拦下——它一改，请求体里最大的一块就变了，前缀缓存跟着作废。ST 升级后这两个脚本都要重跑，fixture 也要重抓。
- **只认 OpenAI 形状的响应**。Claude、Gemini 原生连接下会直接报 `SESSION_PROVIDER_UNSUPPORTED`——服务端做的是请求侧转换，响应形状跟着后端走，ST 自己的解析链也分开写。做四种形状等于猜。
- **直连绕过了 ST 的发送锁**。用户可以同时发消息，两个请求同时在飞；我们只做会话**内部**的互斥（一场跑着就不许再开一场），跨 ST 主请求的互斥没有做。
- **不落盘、没有界面**。会话只活在内存里，刷新即丢；能看到的只有结束那一行摘要和 `/thrive session log` 的全文。
- **工具是 stub**。`stub_read` 发一张票、`stub_write` 认票——这是故意的：让"必须两轮"成为结构事实（不认票就没法写），而不是"希望模型先读后写"这种靠行为押注的东西。接真实学习时换成真的工具表即可，`runLoop` 不用动。

## ADR-050 · 对话与学习分离：学习在一次性会话里跑，聊天侧零痕迹

**背景**：ADR-049 把"一场能自己带预设、自己带工具、不碰当前聊天"的会话做出来了，但当时它还只是个框架——预设、用户消息、工具全是 stub，学习仍然挂在聊天请求里。继续这么挂着，前面所有隔离的努力都白做：学习块进 system 区、工具定义进 `tools`、工具日志进 `mes`，聊天请求与"学不学"始终绑在一起。

同时暴露出第二个问题：**模式太多**。主动 / 被动两套开关，加上"借下一轮"的临时记号，用户要同时理解三个概念才能回答"它到底会不会学"。而它们回答的其实是同一个问题。

**决策**：学习整体搬到一次性会话里，聊天请求里**没有任何插件痕迹**；同时把模式收敛成一个总开关。

**一、单开关**

- 只有**学习模式**一个开关，按对话记（`chat_metadata`）。没有主动 / 被动之分，也没有"只借这一轮"。
- 语义是"要不要自动学"，不是"能不能学"：关着也能手动学一次，只是不会自己触发。
- 两个旧开关合并时取**或**：以前"被动开着"的人，升级后想要的就是"学习模式开着"。

**二、触发**

- 两条判据（每 N 条 / 关键词）是 or 关系，**全局**（对所有对话一致），住在设置页。
- 只在**角色回复完之后**评估。学习是独立会话，不必抢在生成之前；放在回复之后既不会和正在生成的聊天抢同一个后端，也保证这一轮两边都已经落进记录。
- 同一轮不重复触发：记下这一轮用户消息的哈希。关键词在 AI 的复述里再出现一次，不该连着学两遍。
- 手动「立刻学一次」走同一条链路，只换触发原因——这样"配完判据能不能生效"是可验证的，不必等下一次真出现那句话。

**三、预设即消息列**

- 提示词卡片不再是"注入到某个位置的一段文字"，而是**一场会话里的消息**：按 `promptOrder` 一条一张卡，每条自带 role，宏在发请求前逐段展开。
- 卡片里只有两张内置卡：**学习规则**（做什么、产出走哪、写到哪、怎么写）与**目标内容**（只存描述行）。压缩将来复用同一份规则，所以规则里不写任何"这一轮学多少"的动态内容。
- 目标内容的正文由运行时给，学习时是**当前对话记录合并成的一条消息**（`名字：内容`）。合并是刻意的：拆成几十条，模型会把它当成"正在进行的对话"，而不是"待处理的材料"。
- 开场白（User 消息）不属于预设，它是预设之后的第一条消息，在提示词编辑器里单独编辑、学习和压缩各一段。
- 停用 = 不进预设，正文一个字不动；空串 = 用默认文本，这样默认文案随版本更新时老用户也能拿到新版。

**四、产出只走工具**

- 会话里模型的正文没人看，可以完全不写；**一个工具都不调用也算正常**（没有值得记的内容）。因此 `runLoop` 把"没有工具调用"当成正常终止，空正文不入栈。
- 工具不进 `ToolManager`、不进聊天请求的 `tools`：它们在 `tools.js` 里是一张定义表，由 `session-tools.js` 包装成会话私有工具。守卫因此从"每请求判断该不该注册"变成"现在有没有一场学习在跑"。
- 工具写完直接落盘（世界书即时写、描述走 patch），因为会话本身不落盘。

**五、压缩共用框架**

压缩不单独做一套：换掉的只是"目标内容从哪来"（超长条目的正文）与"开场白是哪段"。这一版只把提示词的位置留好（`compactUserMessage` 可编辑），智能压缩本身仍未接线。

**被它废掉的条款**：

| 旧条款 | 现在 |
|---|---|
| ADR-001 注入落对话尾部、`shouldRegister` 门控 | 不注入、不注册；工具按"有没有学习在跑"判可用 |
| ADR-031 学习块按运行模式拆段 | 只有一份通用规则，没有模式可拆 |
| ADR-037 工具常驻：把"能不能用"搬进提示词 | 删掉。聊天请求里没有工具定义，常驻与缓存都无从谈起 |
| ADR-038 卡片排序 + 一道分界线（系统区 / 尾部） | 线性顺序，没有落点之分 |
| ADR-044 被动开关按对话记 | 合并进学习模式总开关（取或） |
| ADR-045 判据在设置页、落点进面板 | 判据仍全局、仍在设置页；面板多了"立刻学一次"与"停止" |
| ADR-048 提示词按角色切段、有损导入保留落点 | 角色仍保留（就是消息的 role）；导入不再有"落点"，内容夹在两张内置卡之间 |

**理由**：

- **为什么"零痕迹"值得单独做**：只要聊天请求里还有插件的东西，前缀缓存就会随"学不学"变化，删一条消息就可能动学习输入，后处理模式也能改写它。三件事都消失之后，"插件对聊天不可见"从口号变成了结构事实。
- **为什么只留一个开关**：三个开关能组合出八种状态，而其中只有两种在语义上不同（学 / 不学）。一次学好几次的差别交给判据，而不是交给"模式"。
- **为什么判据全局、开关对话级**："我隔多久想让它学一次"是人的习惯，"这一场要不要学"是这一场的事。前者改一次处处生效，后者各场各管。
- **为什么合并成一条目标内容**：模型的注意力是按消息分配的。几十条 `role: user/assistant` 的消息会被读成"一段还没说完的对话"，它接着往下聊；一条长文本才读成"材料"。
- **为什么不把开场白也塞进预设**：它是"这一次要你做什么"，而预设是"你是谁、规矩是什么"。混在一起之后，压缩想换开场白就得动预设，而学习与压缩的差别恰恰只在开场白。
- **为什么空回复算成功**：这一轮没有值得记的东西是正常结论。把它当失败会逼模型为了"有产出"而硬写，那比不写更糟。

**代价**：

- **判据只在回复后评估**，所以"每 N 条"的触发点比"每 N 条"晚半轮；第一次评估时基线还在对齐。
- **切换对话必须中止正在跑的那一场**：工具写的是"当前对话"的 `chat_metadata`（可写书、读取登记），跑到一半换场就可能把内容写进另一个角色。
- **结果只有摘要**：会话不落盘、没有界面，能看到的只有"几次工具调用 / 几轮 / 有没有跑完"，以及世界书与描述里的实际变化。要复盘得看 `/thrive status` 或直接看「已写入」。
- **提示词改了就要重新理解**：旧的"自动注入 / 工具常驻 / 分界线"设置会被迁移（判据搬过去、其余删掉），但用户原来精心排的落点没有对应物，顺序只能按原来的相对次序保留。

## ADR-051 · 教授：目标内容也可以不是对话记录

**背景**：ADR-050 之后，"学习"的唯一输入是当前对话记录。这在"从聊天里提炼设定"时是对的，但把使用场景框死了一半：

- 有些东西**聊天里还没发生过**。你想让角色记住"雾港"是什么，可这段对话压根没聊到雾港，得先编几句话让角色说出来、再让它学——为了教一个设定，先污染一段聊天。
- 有些东西**一句话说不清，一张图就够**。人物立绘、场景概念图、界面截图，写成文字既失真又冗长。
- 有些东西**不该算进学习进度**。你补一条设定，和"这段聊天已经被消化过"是两件事；后者才该推进基线。

**决策**：加一个手动入口「教授」。目标内容换成用户写的一段话（可附图），其余复用同一条链路。

**一、只换目标来源**

`buildTeachTarget()` 产出 `{ text, images }`，`buildPreset(settings, { target: text })` 照旧编译预设。学习规则卡、自建卡、开场白、工具表、轮数上限、结果摘要——一样都不换。压缩将来也走这条路（换目标来源 + 换开场白）。

**二、图片挂在开场白上，不进预设**

预设是 `{ role, text }[]` 的纯文本列，塞不进二进制。硬要给 run 加一个 `images` 字段，等于让每一层（编译、协议自检、估算、日志）都多认一种形状，而收益只是"图片在列表里更靠前一点"。

所以图片挂在这一场会话的**开场白**那条 User 消息上：`content` 变成 `[{type:'text'},{type:'image_url'}]` 的块数组。它在整份预设之后发出，正好是"规则 → 材料 → 这次要你做什么（连同图）"的最后一步。为了让模型知道还有图，目标内容末尾补一句"附了 N 张图，在下面这条消息里"。

代价是 `session-messages.js` 要放宽一条协议不变式：**只有 user 消息**的 `content` 可以是块数组，块只认 text / image_url，image_url 必须是 data URL。`assertProtocol` 照旧在每一轮之后跑。

**三、图片用 data URL，且先缩**

会话不落盘，也不引用 ST 的 `user/images/` 目录——那套路径属于聊天消息，删一条消息或换一个对话就可能失效。所以文件读进来直接转 data URL。

太大的图还要先缩（≥700 KB 或边长 >1400 px → 缩到 1400 px 内、JPEG 0.86）。**token 估算不能按 base64 长度算**：一张 1024×768 的 JPEG 编码后 30 万字符，除 3 就是十万 token，预算判定会立刻判"装不下"，而真实开销是一千上下。所以估算时先把 data URL 换成固定占位串，再按张数补 `IMAGE_TOKENS`（1100，按 512 px 切块口径略偏高）。

**四、教授不动学习进度**

不调 `beginLearn`：基线不动、`lastHash` 不记。理由很直接——教一次不等于这一段聊天被看过；把基线推上去，下次该触发的自动学习就会跳过它。

结果照常写 `lastRun`，但 `reason = 'teach'`，面板与徽章说"上次教授…"。这也是唯一需要区分两种手动触发的地方：用户得能看出上次那次是学聊天还是听我讲。

**被它改掉的条款**：

| 旧条款 | 现在 |
|---|---|
| ADR-050 "目标内容 = 当前对话记录" | 两种来源：对话记录，或用户写的一段话（可附图） |
| ADR-049 消息段的形状只有 `{role, content: string}` | user 消息的 `content` 还可以是多模态块数组 |
| ADR-050 "手动入口只有一个「立刻学一次」" | 两个：立刻学一次 / 教授 |

**理由**：

- **为什么不复用「立刻学一次」加个输入框**：两者的目标内容不同、对对话状态的影响也不同（一个推基线、一个不动）。合在一个按钮里，用户永远说不清刚才那一下算不算"学过这一段"。
- **为什么不做成"再开一场空对话让它学"**：那就把聊天记录又拖回来了，而且会把临时内容留在用户的对话列表里。
- **为什么图不单独发一条消息**：图和它对应的那段话分在两条消息里，模型会把它们当成两件事。
- **为什么是 4 张、6000 字**：再多就不是"教一件事"，是该拆成几次；上限存在的意义是让人动手拆，而不是让人抱怨截断。

**代价**：

- **多模态依赖后端**：非视觉模型看到 `image_url` 块会报 400。这里不做模型能力探测——`canPerformToolCalls` 只回答工具，没有对应的视觉探测接口，猜错的代价（把图悄悄丢掉）比报错更糟。
- **图片会占预算**：每张按 1100 token 估，四张就是 4400，小上下文模型可能因此提前收手。
- **教授的内容不留档**：会话结束就没了，只有工具写下的结果与世界书 / 描述里的变化。要重教一次得重新写。
- **面板宽度有限**：教授窗口是独立窗口，不是面板内嵌的一块——面板要写一段话太窄，做成侧栏又只为一个低频动作用。

## ADR-052 · 连接配置、串行排队、撤掉环境诊断

**背景**：ADR-049 / ADR-050 把学习挪进插件自己发起的一次性会话之后，三件事浮上来：

- **会话跟着谁走？** 请求"跟着当前聊天设置"走，也就是跟着 ST 主界面此刻选的那个 API。可用户常常用 A 模型聊天、想用 B 模型学习（更便宜、上下文更长、更会调工具）。以前没得选。
- **多出来的触发去哪？** 判据可能连着命中（条数判据与关键词同时到达），用户也可能手快连点两下。同一时刻只允许一场，那第二场怎么办？以前是直接拒掉（`SESSION_BUSY`）——用户点了按钮，得到的是一句"已经有一场在跑了"。
- **还要不要预判"能不能跑"？** 设置页顶那块诊断读 `ctx.isToolCallingSupported()`，可会话的 `tools` 是我们自己写进 payload 的，ST 那个「启用函数调用」开关管不到它。用户把开关关掉，学习其实照样能跑，界面却写着"工具调用不可用，开了也学不了"。

**一、连接配置：一场会话只走一条路**

设置页新增「API 连接」组，一个下拉，存 `connectionProfile`（全局）：

- 空串（默认）= 跟随当前聊天设置：`createGenerationParameters` 造 payload，直连 `/api/backends/chat-completions/generate`。
- 非空 = 某一份连接配置的 id：交给 `ConnectionManagerRequestService.sendRequest`，由它把 profile 的 api / 模型 / 密钥 / 代理 / 端点映射成请求。**预设不随行**（`includePreset: false`）——它属于"聊天那边"的提示词，会话有自己编译的一份，两套一起发等于给模型两条打架的规则。

`profileId` 在 `openSession` 时读一次就**定死**，整场不换。中途换路会让同一场的前后两轮跑到不同模型上，而模型的工具调用习惯是模型级的——一半像 A 一半像 B，出错时根本说不清是谁的错。

下拉只列 `mode === 'cc'` 的配置：文本补全带不了 `tools`，选中之后每场都会以 `SESSION_PROFILE_UNSUPPORTED` 失败，不如一开始就不让它出现在选项里。选中的那份后来被删掉时，下拉留一个占位项而不是悄悄跳回第一项——"以为还用着那份配置"比看见一个红字更糟。

`extractData: false` 是这条路的关键：默认会把响应解析成 `{ content, reasoning }`，`tool_calls` 在解析那一步就丢了。

**二、多出来的触发：排队，串行**

`startLearning` 从"要么开、要么拒"变成三段返回：开起来（带 promise）、排上队（`{ ok: true, queued: N }`，没有 promise）、被拒（队列满了 / 教授内容是空的 / 没对话）。

- 队列是**内存数组**，按 `chatId` 归属，上限 6 场。满了才拒，而且明说"没生效"，不静默丢最新的。
- 出队靠 `pump()`：前一场结束（成、败、被中止都算）时取下一场。取之前核 `chatId`，不属于当前对话的直接丢掉——它写的是那个对话的书，换场之后跑它等于把内容塞到另一个角色身上。
- **不落盘**。排队是"我马上还要学一次"，进程重启后重放没有意义，反而可能把旧内容当成新任务再写一遍。
- **中止连排队的一起清**。只停当前那场的话 `pump()` 会立刻开下一场，用户按的「停止」看起来就像没生效。
- 内容定型的时机按来源分：教授在**入队时**定型（就是用户此刻写下的那段话，等轮到它再取等于让他改一个字都要重排），"学这段对话"在**出队时**现取（要拿最新的记录）。
- 界面不藏按钮：跑着的时候「教授」「立刻学一次」照常可点，状态行后面加一颗「排队 N」。点了没反应，比点了要等更让人困惑。

**三、撤掉环境诊断**

删掉 `diagnoseEnvironment` / `formatDiagnosis` / 设置页顶部那块状态 / 徽章与面板里的"工具调用不可用"分支。理由有两条：

1. 它判的那个开关**管不到**我们的请求。留着它，唯一的效果是在本来能跑的时候拦住用户。
2. 它是**预先猜**。会话真的发不出去时，错误会以 `SESSION_TRANSPORT` / `SESSION_PROFILE_*` / `SESSION_NOT_CONFIGURED` 的形式回来，带 HTTP 状态码和响应正文——那比"猜它不行"准得多，而且只在真出事时出现。

`diagnostics.js` 因此只剩错误码目录（`ERROR_HINTS` + `hintFor`），名字也就名副其实了。

**四、教授窗口支持粘贴**

小改动，但落在同一条"少绕一步"的线上：正文框里 Ctrl+V 贴图直接进草稿，走与「图片」按钮同一条通道（同样受 4 张 / 12 MB 限制，大了先缩）。剪贴板同时有图有字时**只接图并拦掉文字插入**——从网页复制的图文里那段字多半是文件名或网址，塞进正文还得自己删。纯文字粘贴一律不拦：光标在哪插在哪是输入框本来的行为。

**被它改掉的条款**：

| 旧条款 | 现在 |
|---|---|
| ADR-049 "请求一律跟着当前聊天设置走" | 两条路：跟随当前设置，或指定某一份连接配置 |
| ADR-049 / ADR-050 "同时只能有一场，多出来的拒掉（`SESSION_BUSY`）" | 排队串行，上限 6 场 |
| ADR-020 "环境不支持工具调用时不开 / 置灰" | **不再预判**。开着就能点，真发不出去时按请求错误报 |
| spec §13 "设置页诊断" | 整块删除 |
| spec §18 "同时只能有一场" | 排队串行 + 一场一条连接 |

**理由**：

- **为什么不并发**：两个会话同时跑就要并发读写 `chat_metadata`（可写书、读取登记、patch、快照、虚拟世界书缓冲区），而这些都是"读到磁盘 → 改 → 写回"。并发下必然出现后写的覆盖先写的，而且冲突点在别人的仓库里，改不动。串行是这个数据模型下唯一可靠的选择。
- **为什么不持久化队列**：持久化要处理"重启后这些任务还算不算数"——对话可能已经删了、书可能已经改了、教授的那段话可能早就过时。为了省掉一次点击去写一份需要版本兼容的重放日志，不划算。
- **为什么连接配置是全局而不是按对话**：用户换一个角色聊天，不该顺手换掉学习用的后端。反过来"某一段对话想用某个模型"是更少见的诉求，等真有人要再做对话级覆盖。
- **为什么不做"自动选一个便宜模型"**：哪个便宜、哪个够用只有用户知道，猜错的表现是"学出来的东西突然变笨"，而且很难归因。

**代价**：

- **排队是盲区**：界面只说"排队 2"，不说排队的是哪两件。要说清就得给每个任务起标题，而"学这段对话"根本没有标题可起。
- **被中止的那一场不会有产出**：排队的任务一样，`/thrive stop` 之后要重新点。
- **连接配置这条路拿不到采样参数**：`ConnectionManagerRequestService` 用那份配置自己的设置，插件的 `sampling` 覆盖在直连那条路上才有。
- **少了一层"提前拦"**：配置选错了要等第一次请求失败才知道。这是有意的交换——把误报换成漏报到请求那一步，代价是一次失败的请求，收益是本来能跑的时候不会被拦。
